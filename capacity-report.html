1. 口径与方法

评估不把 CPU、连接数、Actor 数分别线性拟合，而把三者按生产行为比例绑定成标准容量单元。 这样单次实验同时包含连接保活、Actor 常驻、业务读写和跨农场访问的交互成本。

维度1U0.9U 认证点3000 万 DAU 峰值
业务 QPS10,0009,000333,333
WebSocket 连接120,000108,0004,000,000
驻留 Actor162,600146,3405,420,000

基础实例数 N = ceil(33.333U ÷ 0.9U) = 38

该除法成立的前提是弱扩展效率可接受。因此实验分两步： 先固定整数配额找单实例安全下界，再保持每实例配额不变，把 Gateway、Farm、Social 扩成 2 倍， 检查总负载能否同步扩成 2 倍。

2.2 硬性通过条件

  • 目标请求发送兑现率 ≥98%。
  • 31 个接口分别满足 P90 <300ms、P99 <500ms。
  • 技术错误率 ≤0.1%；连接数和 Actor 数达到目标。
  • 每个接口、每个发压分片至少 500 个样本。

业务状态冲突不作为技术故障；报告中的认证轮仍优先使用夹具干净、错误为零的结果。

5.1 扩展效率应如何表述

单实例认证容量 C₁=0.9U。双实例在 1.6U 已经失败，因此双实例 SLO 容量 C₂<1.6U：

E_capacity = C₂ ÷ (2 × C₁) < 1.6 ÷ 1.8 = 88.9%

这只是上界，不是精确效率；没有双实例通过点，不能严谨地写成 71% 或其他单值。 而且本轮只扩了应用，未扩 MySQL/Redis，测得的是“应用扩容、数据层共享”的半扩展拓扑。

6. MySQL 锁竞争优化

性能数据库的语句摘要定位到热点： DELETE FROM farm_outbox WHERE event_id IN (...) 的锁等待占总耗时 96.5%。 原索引以 published_at 开头，而所有待投递行该字段均为 NULL； 两个 Farm dispatcher 会在同一索引区间执行 claim 与 DELETE。

阶段改动DELETE 锁等待占比单次 DELETE系统行锁等待结果
初始REPEATABLE READ + 共享热区96.5%22.5ms23.4/s严重竞争
RC 探针READ COMMITTED，消除 next-key gap lock51.4%1.0ms10–12/s单语句快约 22×
实例分区增加 producer_farm_id，claim/ack 限定实例索引区间28.2%0.94ms7.9/s跨实例锁区间隔离

分区实现没有动态创建 N 张表，而是在同表增加 producer_farm_id， 索引改为 (producer_farm_id, published_at, dead_lettered_at, next_attempt_at, created_at)。 该方式具备相同的锁区间隔离效果，同时更容易迁移、备份和扩容。

锁优化是真实有效的，但 1.8U P99 仍停在约 1.37 秒，说明 outbox 锁不是唯一瓶颈。 当前最合理的下一步不是继续微调 DELETE，而是把 MySQL、Redis journal 与 Farm 一起按 UID 分片， 再重复弱扩展实验。

7. 3000 万 DAU 容量规划

7.1 应用层基础规划

按 0.9U 认证点做容量除法需要 38 组。考虑双分片时 Farm CPU 增加 14.6%， 不建议继续使用 3C 卡在 81% 水位；将 Farm 调为 4C 后，实测同负载 CPU 水位约 61%。

7.2 三可用区容量

若要求任意一个可用区失效后仍保有全部基础容量，应用数量按 1.5 倍配置： Gateway 57、Farm 57、Social 36，三者合计约 435C / 1,176GiB。 这是容量冗余；MySQL、Redis 的副本数还需按各自高可用协议另算。

7.3 数据层必须单独规划

  • 证据最保守的方案：MySQL 写分片与 38 个 Farm 分片一一对齐；每个分片承接约 0.9U。减少 MySQL 分片数前，必须补测 2 Farm : 1 MySQL 的生产耐久配置。
  • Redis journal：流键已经按 Farm 实例隔离，生产应把 keyspace 或实例也按 Farm 分片拆分，避免把 38 份单线程负载压到一个 Redis 主节点。
  • Redis data / presence：按 UID 一致性哈希分片；容量由最热分片命令率和内存决定，不按应用 Pod 数机械相乘。
  • MySQL 内存：本轮 2.92–3.74GiB 只反映测试数据集，不代表 3000 万用户的数据工作集；生产内存、磁盘和 IOPS 必须按数据量、索引量、保留期另算。
推荐落地口径： 先按 38 Gateway + 38 Farm + 24 Social 做应用采购基线； Farm 用 4C 而不是 3C。数据层以 38 个 UID 分区为安全起点， 在目标硬件上通过“2 Farm : 1 DB”“4 Farm : 1 DB”阶梯实验后再合并分区，不能直接假设共享数据库线性扩展。

8. 风险、边界与验收项

当前报告是容量实验结论，不是生产上线签字。最关键的缺口是： 双实例实验没有同步扩展数据层，因此完整 2 倍弱扩展尚未通过。
  1. 生产耐久性：测试使用 innodb_flush_log_at_trx_commit=2、sync_binlog=0、innodb_doublewrite=OFF。生产若要求事务与 binlog 强持久，需恢复安全设置并重测；容量只会持平或下降。
  2. 快速轮用途：45 秒分区轮满足最低样本数，只用于筛选；最终放行需 180 秒标准轮和至少 600 秒浸泡轮。
  3. 跨节点网络：单节点 K3s 未覆盖真实跨节点 RTT、负载均衡器、可用区网络和数十实例连接矩阵。
  4. 分片偏斜：1024 逻辑片映射到 38 个 Farm 时不能完全均分；最热实例为 27 片，相对理想均值约高 0.2%，影响很小。
  5. 行为模型：结果只适用于当前 31 接口权重、连接密度和 Actor 保留策略。埋点校准后若会话时长、操作频率或跨农场占比变化，应重新计算 U。
  6. 下一次标准验收：2×Gateway、2×Farm、2×MySQL 分区、2×Redis journal 分区，在 1.8U 跑 180 秒；通过后才能把 2 倍扩展效率写成 100% 附近的实测值。
