# 农场游戏用户行为与混合压测模型 v2

状态：评审稿，确认后再实现压测脚本和执行测试  
基线模型：`user-behavior.normal-v1.json`  
适用范围：H5 客户端、Gateway、Farm、Social、MySQL、Redis 的端到端容量与稳定性验证

> 口径说明：本文保留 `normal-v1` 的峰值系数1.5、27.7059次/会话和69,264.65 QPS，用于记录31接口历史比例与技术细节；当前答辩主口径采用峰值系数2.0和每会话60次请求，统一按约200,000 QPS计算，不再区分常态、高活跃两种全站口径。后续实现时以答辩模型的六类组权重为总量，再复用本文记录的组内接口比例。

## 1. 目标与边界

本文档定义两件相互关联、但不能混为一谈的模型：

1. **用户行为模型**：描述 3,000 万 DAU 在峰值时有多少在线用户、会话和业务行为，不依赖某台测试机器的 CPU 或副本数。
2. **压测执行模型**：描述如何把用户行为缩放到本地 K3s 的固定资源单元，如何准备数据、发压、判定稳定和输出报告。

本模型用于回答：

- 峰值时各业务行为的合理比例是什么；
- 单个固定资源单元的稳定业务 QPS 是多少；
- 接口之间是否发生队头阻塞、锁竞争、投影积压和资源争用；
- 如何从单容量单元推导生产容量下限。

本模型不用于声称本地 K3s 已真实承载 3,000 万用户。本地测试只验证单容量单元；生产总容量还要同时受连接数、驻留 Actor、数据分片、存储吞吐和故障域约束。

## 3. 人口、会话与连接模型

### 3.1 基础假设

| 参数 | 数值 | 来源 | 说明 |
|---|---:|---|---|
| DAU | 30,000,000 | requirement | 项目目标 |
| 每 DAU 每日会话 | 2.0 | assumption | 无生产埋点 |
| 平均会话时长 | 20 分钟 | assumption | 由人物模型加权得到 |
| 每日主要活跃窗口 | 10 小时 | assumption | 夜间低活跃不计入主要窗口 |
| 窗口内峰值系数 | 1.5 | assumption | 无生产埋点 |
| 重连占新会话比例 | 10% | assumption | 网络波动基线 |
| WebSocket Ping 间隔 | 30 秒 | product | 需与代码配置保持一致 |

10小时活跃窗口平均会话到达率：

```text
30,000,000 × 2 / (10 × 3,600) = 1,666.67 sessions/s
```

峰值会话到达率：

```text
1,666.67 × 1.5 = 2,500 sessions/s
```

10小时活跃窗口平均在线人数：

```text
30,000,000 × 2 × 20 / (10 × 60) = 2,000,000
```

峰值在线人数：

```text
2,000,000 × 1.5 = 3,000,000 PCU
```

这与旧模型的 `全天平均 × 3.6` 数值等价，因为 `3.6 = 24 / 10 × 1.5`。v2 将它拆成活跃窗口和窗口内峰值，避免重复计算夜间低谷和白天峰值。

峰值连接与启动负载：

| 负载 | 峰值 |
|---|---:|
| 活跃 WebSocket | 3,000,000 |
| 新会话 | 2,500/s |
| 额外重连 | 250/s |
| WebSocket Handshake | 2,750/s |
| 服务端 Ping | 100,000/s |
| 客户端 Pong | 100,000/s |

登录、握手、Ping/Pong 属于连接/启动负载，不计入后面的 69,264.65 业务 QPS，必须单独测试或在组合场景中显式叠加。

|---|---:|---:|---:|---:|
| quick | 35% | 8 分钟 | 14% | 13.989 |

在线占比由 `会话占比 × 会话时长` 归一化得到，不单独手填。人物定义如下：

- `quick`：短时进入、查看任务邮件、少量收获或商店操作后离开；
- `routine`：完成一到数轮本地农场操作，并进行少量社交访问；
- `social`：好友列表、访问好友和跨农场操作明显更多；
- `heavy`：长时间在线，本地循环、宠物、任务、图鉴和社交操作都更频繁。

## 5. 状态化用户工作流

### 5.1 会话启动

```text
Register（仅 2.5% 新账号）或 Login
→ WebSocket Handshake
→ EnterSelf
→ TaskList / MailList / PetStatus（按人物概率）
→ 进入本地或社交工作流
```

注册占新会话 2.5%，登录占 97.5%。注册、登录和握手在启动场景中测试，不重复计入稳态业务混合流量。

### 5.2 导航与同步

```text
EnterSelf
├─ 本地 Farm 状态新鲜：后续 Sync 可走快速路径
└─ Actor 冷或快照失效：执行快照恢复

FriendList
→ EnterFriend
→ 跨农场操作

客户端序号落后
→ Sync
```

普通场景初始 Actor 命中假设：自己农场 90% 热、10% 冷；好友农场 70% 热、30% 冷。该比例来源为 `assumption`，必须在报告中单独展示。另设纯冷启动场景，不在普通场景中偷偷改变比例。

### 5.3 本地农场状态机

```text
空地且未整理 → Clear/Till
已整理 → Plant
生长中且缺水 → WaterLocal
生长中且有杂草 → WeedLocal
生长中且有虫害 → PestLocal
满足施肥条件 → Fertilize
成熟 → Harvest
Harvest 后重新进入 Clear/Till
```

每次只选择当前状态允许的动作。初始地块状态按第 6 节本地农场接口占比反向准备，保证测量窗口内目标比例可以持续，而不是大量返回“不允许操作”。

### 5.4 跨农场状态机

```text
FriendList
→ EnterFriend
→ AreFriends/权限验证
→ WaterCross / WeedCross / PestCross / Steal
→ 根据返回状态更新本地客户端模型
```

同一个好友地块不能被无限偷取或重复除虫。驱动必须为每次操作预留合法目标；没有合法目标时记为“夹具耗尽”，不得算作服务器性能错误，也不得继续把这轮作为有效容量结果。

### 5.5 任务

```text
TaskList
├─ 73.05%：只查看或没有可领取任务
└─ 26.95%：TaskClaim
```

`26.95% = 0.6475 / 2.4025`。每个 Claim 使用尚未领取且前置进度满足的任务。并发一致性专项场景允许多个请求竞争同一任务；普通容量场景不制造这种人为冲突。

### 5.6 邮件

```text
MailList
├─ 17.75%：MailRead
├─ 6.11%：MailClaim
└─ 1.43%：MailDelete
```

条件概率分别由 `MailRead/MailList`、`MailClaim/MailList` 和 `MailDelete/MailList` 得到。三类邮件使用不同 ID，普通场景不对同一封邮件重复消费。

### 5.7 商店、宠物、图鉴和社交元数据

- Buy 前保证余额充足且库存规则允许，Sell 前保证物品数量充足；
- PetFeed 前保证宠物已激活且道具存在，PetActivate 使用一次性宠物状态池；
- FriendList、SearchUser、ListFriendRequests 使用不同规模的数据集覆盖响应体差异；
- RequestFriend、AcceptFriendRequest、RejectFriendRequest、RemoveFriend 和 AcceptInvite 会破坏关系，只在专用一次性社交工作流中运行；
- CodexList 作为读路径加入常态混合流量。

### 5.8 思考时间与到达分布

真实密度场景使用：

- 会话到达：Poisson；
- 工作流次数：以表中均值为参数的 Poisson，重度行为可使用负二项分布补充长尾；
- 同工作流步骤间思考时间：对数正态分布，中位数 0.8 秒、P95 3 秒；
- 工作流之间包含空闲间隔，使总动作数和会话时长同时满足人物模型。

容量加速场景不使用真实墙钟思考时间，由全局开环调度器控制工作流到达率，但仍保持工作流依赖和单连接顺序。

## 7. 从业务模型缩放到压测 QPS

常态混合场景中，第 i 个接口的测试 QPS 为：

```text
test_qps_i = test_total_qps × reference_qps_i / 69,264.65
```

例如总压测 6,800 QPS：

```text
TaskClaim = 6,800 × 1,618.75 / 69,264.65 = 158.92/s
MailClaim = 6,800 × 326.25 / 69,264.65 = 32.03/s
```

工作流驱动允许短窗口内随机波动，但每 10 秒和整个测量窗口的实际接口比例与目标比例偏差应分别不超过 10% 和 3%；低于 5 QPS 的接口按实际样本数解释，不强制短窗口误差。

## 8. 数据规模、热点与缓存模型

### 8.1 容量单元账号

标准容量单元使用 15,000 条活跃 WebSocket，按峰值在线占比分配：

| 人物 | 连接数 |
|---|---:|
| quick | 2,100 |
| routine | 6,000 |
| social | 4,500 |
| heavy | 2,400 |

另准备 5,000 个无 WebSocket 的好友目标账号。跨农场目标中 50% 指向活跃账号，50% 指向离线好友池，使单 Farm 最多覆盖约 20,000 个潜在 Actor，与当前 `FARM_ACTOR_MAX_RESIDENT=20000` 对齐。

### 8.2 好友热点

普通场景的暂定分布：60% 跨农场请求落到 20% 的目标农场，其余 40% 均匀分布。热点专项场景改为 50% 请求落到最热 1% 农场，其余请求保持普通分布。

这些比例来源为 `assumption`。报告必须输出目标 UID 的实际请求分布、最热 UID QPS 和 Top 1% 请求占比。

### 8.3 响应数据量

数据生成器至少覆盖小、中、大三档账号：20% 使用最小业务数据，60% 使用产品常态数据，20% 使用当前产品配置允许的高位数据。好友数、邮件数、背包物品、任务数、已解锁地块和图鉴大小从服务端配置读取，不在模型里复制易过期的硬编码上限。

报告按接口记录响应字节 P50/P95/P99，防止只测到小响应缓存路径。

### 8.4 一次性资源准备量

对 Claim、Steal、PetActivate、社交关系写等会消费状态的操作：

```text
required_state_i = ceil(test_qps_i × duration_seconds × 1.2)
```

1.2 是准备余量。准备量不足时，场景启动前直接失败，不能进入测量窗口。

示例：6,800 QPS、60 秒容量测试至少需要：

```text
TaskClaim: ceil(158.92 × 60 × 1.2) = 11,443 个合法领取机会
MailClaim: ceil(32.03 × 60 × 1.2) = 2,307 个合法领取机会
```

测量窗口内禁止使用直接写 MySQL/Redis 的后台脚本补状态。若业务状态可以通过正常接口循环恢复，则恢复操作必须计入行为模型和总 QPS。

## 9. 标准压测场景

### 9.1 S0：空闲基线

- 持续 60 秒；
- 无业务请求，仅保留服务后台任务；
- 记录各服务 CPU、内存、GC、MySQL statements 和 Redis commands 的空闲速率；
- 后续服务需求计算先扣除该基线。

### 9.2 S1：真实密度常态峰值

目的：验证真实的人均速率、Actor 密度、缓存和连接资源。

15,000 连接占 300 万 PCU 的 0.5%，因此：

```text
业务 QPS = 69,264.65 × 0.005 = 346.32
新会话 = 2,500 × 0.005 = 12.50/s
额外重连 = 250 × 0.005 = 1.25/s
Handshake = 13.75/s
Ping/Pong = 各 500/s
```

- 到达分布：Poisson；
- 持续时间：至少 30 分钟；
- 使用真实思考时间和人物在线占比；
- 判定重点：连接稳定、Actor 数、内存、缓存命中、后台积压和长期错误。

### 9.3 S2：单实例容量加速

目的：在固定拓扑下寻找稳定业务 QPS 和越界点。

- 15,000 固定连接；
- 常态 31 项操作比例；
- 到达方式：constant open-loop；
- 快速阶梯每档 30 秒；
- 候选稳定档在可持续夹具完成后执行 3 轮 × 60 秒；
- 每档前等待 lag/pending 为 0，完整重置状态并重启 Farm 清空热 Actor；
- 每条连接内部保持请求顺序。

当前 1 CPU 的建议收敛阶梯为：

```text
5,000 → 6,500 → 6,800 → 7,000 → 7,500 QPS
```

现有两轮 6,800 QPS、30 秒结果仅作为候选参考，不在 v2 正式复测前写成最终容量。

### 9.4 S3：任务/邮件集中领取

模拟每日任务刷新、补偿邮件或活动奖励后的 5 分钟突发：

| 操作 | 相对常态倍率 |
|---|---:|
| TaskList | 2.0× |
| TaskClaim | 3.0× |
| MailList | 1.5× |
| MailClaim | 3.0× |
| 其他操作 | 1.0× |

该组合使总业务 QPS 约增加 18.1%。倍率来源为 `assumption`，不纳入 normal 场景，也不能替代 Claim 并发一致性专项测试。

### 9.5 S4：重连风暴

- 背景保持 S1 常态业务；
- 基线额外重连为 1.25/s；
- 轻度故障：60 秒内重连 5% 活跃连接，即额外 12.5/s；
- 重度故障：60 秒内重连 10% 活跃连接，即额外 25/s；
- 重连后必须完成 Login/Session 恢复、Handshake、EnterSelf 和必要快照恢复；
- 检查 Gateway readiness、Redis 会话、Farm 流重连和 Actor 冷启动。

### 9.6 S5：热门好友农场

- 总 QPS 和接口比例与 S1 或 S2 相同；
- 50% 跨农场请求指向最热 1% 目标 UID；
- 检查单 Actor 邮箱、同地块竞争、跨农场事务编排和热点缓存；
- 业务冲突返回码与系统错误分别统计。

### 9.7 S6：破坏性社交写

- 使用独立的未关联账号对和邀请数据；
- 按第 6 节 630.27 QPS 的生产参考比例缩放；
- 每对关系只消费一次；
- 测试后不复用该夹具；
- 结果与常态混合场景合并用于容量估算，但单独报告。

### 9.8 S7：规划点耐久测试

- 持续 30 分钟，条件允许时扩展到 2 小时；
- 负载取已经验证的稳定 QPS × 70%，而不是容量边界；
- 必须预先通过一次性资源准备量校验；
- 重点检查内存增长、Goroutine、连接泄漏、MySQL连接池、Redis内存、Stream lag 和定时任务干扰。

## 10. 固定测试环境与变量控制

每份结果必须记录：

- Git commit、是否有未提交修改、镜像摘要；
- Gateway/Farm/Social 副本数和每副本 CPU/内存；
- MySQL/Redis 副本和资源；
- `GOMAXPROCS`、投影器数量、Actor TTL、Actor 上限和写入并发参数；
- 行为模型版本、场景版本、夹具版本和随机种子；
- 压测 Pod 资源、节点型号和同节点其他工作负载；
- 连接数、账号数、目标 UID 分布、数据大小分布；
- 预热方式、时间配置和每档重置流程。

比较代码优化前后时，除 Git commit 外其他变量必须相同。改变 CPU、投影器、账号量、时长或缓存温度后，不得直接计算“代码性能提升百分比”。

## 11. 标准执行流程

每个正式档位执行：

1. 检查所有服务 Ready，记录资源拓扑和配置；
2. 等待 Farm journal lag/pending、Claim waiters 和压测端残留连接归零；
3. 校验一次性资源准备量；
4. 重置专用账号，禁止使用业务账号；
5. 按场景决定是否重启 Farm、清空 Actor 或保留真实热度；
6. 建立固定连接并按人物在线占比分配；
7. 预热自己农场、好友农场、任务和邮件读路径；
8. 静置 2 秒并保存测量前指标快照；
9. 开环启动工作流，记录计划到达和实际发送；
10. 测量结束后停止新工作流，等待队列排空；
11. 保存结果、Prometheus 时间窗口、日志和依赖指标；
12. 确认 journal lag/pending 回到 0；
13. 候选稳定档更换随机种子并重复 3 轮。

若预热、夹具、发压器或依赖发生异常，该轮标记为 invalid，不以“服务失败”或“服务通过”计入容量表。

## 12. 指标与错误分类

### 12.1 客户端和业务指标

- target/scheduled/started/sent/completed QPS；
- completion QPS 和 drain time；
- 整体及逐接口 Avg、P50、P90、P95、P99、Max；
- 响应字节 P50/P95/P99；
- 业务错误码、系统错误、客户端排队丢弃和超时分别统计；
- 每人物、每工作流、每目标热度分组统计。

### 12.2 Gateway

- WebSocket 连接、握手、重连和异常关闭；
- Farm/Social 长流数量、队列深度和重连次数；
- CPU、CPU throttling、内存、GC、Goroutine；
- 协议编解码和请求聚合延迟。

### 12.3 Farm

- Actor resident、创建、回收和邮箱深度；
- normal/barrier lane 队列、in-flight、queue wait；
- Claim barrier waiters 和等待时间；
- write journal append、lag、pending、projection active/limit；
- 每类投影 batch、records 和 MySQL耗时；
- CPU、throttling、内存、GC、Goroutine。

### 12.4 MySQL 与 Redis

- MySQL statements/s、transactions/s、连接池等待、threads running；
- 慢查询、行锁等待、死锁、buffer pool命中和磁盘延迟；
- Redis commands/s、命令延迟、连接数、CPU、内存、eviction；
- Stream 长度、consumer lag、pending 和 reclaim。

## 13. 暂定验收与稳定线

在产品没有正式 SLA 前，使用以下工程验收线：

| 指标 | 常态容量验收 |
|---|---:|
| 系统错误率 | ≤ 0.1% |
| 整体 P90 | ≤ 100 ms |
| 整体 P99 | ≤ 250 ms |
| TaskClaim P95 | ≤ 500 ms |
| MailClaim P95 | ≤ 500 ms |
| 排空时间 | ≤ 1 秒 |
| 测量后 lag/pending | 1 秒内回到 0 |
| 发压完成率 | ≥ 99.5% |

Avg、P50、P95 和 Max 必须报告，但 Avg 不作为单独通过门槛。业务预期的 `Avg≈50 ms、P90≈100 ms、P99≈200 ms` 是观察目标，不要求三个数同时命中。

稳定 QPS 定义为：相同拓扑、相同模型、不同随机种子的 3 轮测试全部满足验收线，且延迟、CPU、队列和 lag 不随时间持续增长的最高档位。容量边界是第一个失败档，不得作为稳定吞吐。

生产规划点默认取：

```text
planning_qps = stable_qps × 70%
```

最终副本数不能只按 QPS 计算，必须取以下约束的最大值：

```text
max(业务QPS约束, WebSocket连接约束, 驻留Actor约束,
    MySQL分片约束, Redis吞吐与内存约束, 故障域约束)
```

## 14. 报告结构

每次正式测试报告固定包含：

1. 一页结论：稳定档、越界档、主要瓶颈和是否达到目标；
2. 代码与环境：commit、资源拓扑、镜像和关键配置；
3. 行为模型：人物、工作流、接口比例、来源和置信度；
4. 测试方法：开环方式、连接、夹具、预热、时长、阶梯和随机种子；
5. 阶梯结果：目标/实际 QPS、成功失败、Avg/P90/P95/P99/Max、排空；
6. 逐接口结果：特别列出 Claim、跨农场和写接口；
7. 资源与依赖：CPU、内存、Actor、队列、MySQL、Redis、journal；
8. 瓶颈证据链：时间上相关的指标，不用单点猜测；
9. 容量推导：稳定吞吐、70%规划点、各类容量约束和建议值；
10. 无效测试和限制：夹具耗尽、配置变化、监控缺失等；
11. 复现命令与原始产物路径。

## 15. 模型校准与版本管理

上线后按以下周期更新：

- 每周生成接口次数、会话时长、人物聚类、好友热点和重连率；
- 每月选择普通日、P95 峰值日和活动日形成三个模型；
- 接口或玩法改变时提升模型小版本；人口、人物或场景结构改变时提升大版本；
- 原始埋点查询、生成脚本、生成后的 JSON 和压测报告一起保存；
- 历史报告引用具体模型版本，禁止用新模型覆盖旧报告口径。

需要优先补充的生产埋点：

1. 每会话各接口次数和顺序；
2. 会话时长、空闲间隔和重连次数；
3. 本地/好友访问比例和目标 UID 热度；
4. Task/Mail 可领取率及刷新后 1/5/15 分钟峰值；
5. 好友数、邮件数、背包、地块和响应字节分布；
6. 每 UID 命令并发度和同 UID 连续操作间隔。
