# 农场游戏用户行为与混合压测模型（答辩版）

状态：答辩评审稿，确认后再实现脚本和执行正式测试  
详细技术附录：`USER-BEHAVIOR-AND-LOAD-MODEL-V2.md`

## 1. 一句话说明模型

先用 DAU、每日会话数、会话时长、每日活跃窗口和窗口内峰值系数算出峰值在线人数与会话到达率，再把一次典型会话归纳为六类业务行为，得到全站峰值业务 QPS；压测时保持六类行为比例不变，用开环阶梯压力找出固定资源下的稳定 QPS。

答辩主线只需要讲清楚下面四步：

```text
3,000万 DAU
→ 峰值 400万在线用户、3,333次会话进入/秒
→ 每次会话产生 60 个业务请求
→ 峰值约 200,000 业务QPS
```

## 2. 从 3,000 万 DAU 推导峰值负载

### 2.1 基础假设

由于项目还没有生产埋点，使用一组明确、可替换的假设：

| 参数 | 数值 | 说明 |
|---|---:|---|
| DAU | 30,000,000 | 项目要求 |
| 每人每天会话 | 2 次 | 暂定产品假设 |
| 平均会话时长 | 20 分钟 | 暂定产品假设 |
| 每日主要活跃窗口 | 10 小时 | 夜间低活跃不计入主要流量窗口 |
| 窗口内峰值系数 | 2.0 | 活跃时段峰值是窗口平均值的 2 倍 |
| 断线重连比例 | 10% | 用于连接专项测试 |

答辩时要明确说明：这些不是伪装成生产事实的数据，而是无线上数据时用于容量设计的基线。模型把公式和假设公开，未来拿到埋点后只替换输入，不更换计算方法。

### 2.2 峰值会话进入速率

每天总会话数：

```text
30,000,000 × 2 = 60,000,000 次/天
```

10小时活跃窗口内的平均会话进入速率：

```text
60,000,000 / (10 × 3,600) = 1,666.67 次/秒
```

峰值会话进入速率：

```text
1,666.67 × 2.0 = 3,333.33 次/秒
```

### 2.3 峰值在线人数

10小时活跃窗口内的平均在线人数：

```text
30,000,000 × 2 × 20 / (10 × 60) = 2,000,000
```

峰值在线人数：

```text
2,000,000 × 2.0 = 4,000,000 PCU
```

折算到全天平均口径，当前等效峰值系数为 `24 / 10 × 2.0 = 4.8`。答辩直接使用“10小时活跃窗口 × 2.0”，让夜间低谷和活跃时段内峰值两个因素都能被清楚解释。

因此连接模型为：

| 指标 | 峰值 |
|---|---:|
| WebSocket 在线连接 | 4,000,000 |
| 新会话进入 | 3,333.33/s |
| 额外重连 | 333.33/s |
| Handshake | 3,666.67/s |
| 30秒一次 Ping/Pong | 各 133,333.33/s |

连接、登录和重连单独测试，不混入业务 QPS，避免一个模型同时解释两种完全不同的瓶颈。

## 3. 把一次用户会话简化为六类行为

答辩版不再讲四类人物，也不逐项解释31个接口。根据产品玩法，把一次平均20分钟会话归纳为六类行为。

公开资料可以帮助判断会话时长，却不能直接代替业务请求频率：[GameAnalytics 2026移动与PC游戏基准](https://www.gameanalytics.com/reports/2026-mobile-pc-gaming-benchmarks)包含会话时长、频次和参与度指标；[报告公开PDF](https://investgame.net/news/pdf/2026-01-27-2026-mobile-pc-benchmarks_compressed/)中的2025年数据表明，移动游戏会话中位数约3.1～3.5分钟，而具有深度成长、社交机制的头部游戏会超过22分钟。[AAAI AIIDE 2024发布的 FarmQuest 农场游戏遥测数据](https://ojs.aaai.org/index.php/AIIDE/article/view/31889)包含64次游玩和30类事件，但论文明确说明时间戳不可用，因此也不能从中可靠算出每分钟操作数。由此可见，当前20分钟会话属于有意偏高的容量压力假设，不应表述成行业平均值。

所以本文不把请求频率伪装成“行业标准”，而是使用可解释、可替换的工程假设：农场经营操作通常包含选择目标、发起操作、等待动画或结果、再做下一次决策，按每15～30秒一次有效业务操作估算，合理区间为每分钟2～4次。容量模型只保留中间值每分钟3次，即每20秒一次、20分钟60次业务请求：

| 行为组 | 一次会话平均请求数 | 峰值QPS | 占比 | 包含内容 |
|---|---:|---:|---:|---|
| 进入与同步 | 6 | 20,000.00 | 10.00% | 进入自己农场、进入好友农场、同步 |
| 本地农场循环 | 19 | 63,333.33 | 31.67% | 翻地、清理、播种、浇水、除草、除虫、施肥、收获 |
| 好友与跨农场 | 16 | 53,333.33 | 26.67% | 好友列表、搜索、请求列表、分享、帮忙、偷菜 |
| 任务 | 7 | 23,333.33 | 11.67% | TaskList、TaskClaim |
| 邮件 | 5 | 16,666.67 | 8.33% | MailList、MailRead、MailClaim、MailDelete |
| 商店/宠物/图鉴 | 7 | 23,333.33 | 11.67% | Buy、Sell、Pet、Codex |
| 合计 | 60 | 200,000.00 | 100% | 31个可持续测试接口 |

这张表就是答辩时最重要的行为模型。接口映射来自现有31接口模型，整数化后本地农场和好友玩法占58.34%，任务和邮件占20%，其他入口、商店、宠物和图鉴占21.66%。

峰值业务 QPS 的推导为：

```text
峰值会话进入速率 × 每会话平均请求数
= 3,333.33 × 60
≈ 200,000 QPS
```

加好友、删好友、接受邀请等低频且会破坏测试关系数据的一次性社交写操作，放在独立小场景验证，不混入主混合压测。全站容量只保留上面的20万QPS一种口径。

## 4. 混合压测怎么按比例发请求

压测不需要在一台机器上直接发满200,000 QPS。我们先测试一个固定资源单元能承受多少 QPS，然后再计算容量。

任意测试总 QPS 下：

```text
某行为组QPS = 测试总QPS × 行为组占比
```

例如测试总量为 6,800 QPS：

| 行为组 | 测试QPS |
|---|---:|
| 进入与同步 | 680 |
| 本地农场循环 | 2,153 |
| 好友与跨农场 | 1,813 |
| 任务 | 794 |
| 邮件 | 567 |
| 商店/宠物/图鉴 | 793 |
| 合计 | 6,800 |

行为组内部继续使用现有接口比例。例如任务组中 TaskList 约占78.8%，TaskClaim约占21.2%；邮件组中列表最多，Claim只占较小比例。

驱动必须满足：

- 全局开环发压：服务变慢时仍按计划到达，不能自动降低压力；
- 同一个 WebSocket 内串行，保证客户端序号和同 UID 顺序；
- 不同账号并行；
- 所有写操作使用预先准备的合法状态；
- 系统错误、业务拒绝、客户端丢弃和超时分开统计。

## 5. 只保留三项核心测试

### 5.1 测试一：标准混合容量阶梯

目的：找到固定资源拓扑下的最高稳定 QPS 和第一个越界档。

固定条件：

- 15,000条 WebSocket；
- 六类行为保持标准比例；
- 每档30秒；
- 每档前重置15,000个专用账号；
- 每档前重启 Farm，清空热 Actor；
- 预热连接和农场后静置2秒；
- 测试结束后检查请求排空和 journal lag/pending。

1核 Farm 建议阶梯：

```text
5,000 → 6,500 → 6,800 → 7,000 → 7,500 QPS
```

候选稳定档换随机种子、完整重置后重复3轮。三轮全部通过才写入报告。

### 5.2 测试二：任务/邮件突发

目的：证明已优化的 TaskClaim/MailClaim 不会在集中领取时重新拖垮普通请求。

执行方法：

- 基础压力使用“稳定 QPS × 70%”；
- 进入/农场/好友/其他行为保持不变；
- 任务组整体提高到2倍；
- 邮件组整体提高到2倍；
- 持续30秒；
- 总QPS会比基础压力增加20%。

如果稳定 QPS 为6,800，则基础压力为：

```text
6,800 × 70% = 4,760 QPS
```

任务和邮件加倍后的总压力约为：

```text
4,760 × (1 + 20%) = 5,712 QPS
```

该场景比“单独压 TaskClaim”更有说服力，因为它验证 Claim 突发是否干扰正常种植、好友和读请求。

### 5.3 测试三：规划点稳定性

目的：证明系统不是只能短时达到容量边界。

- 压力使用稳定 QPS × 70%；
- 使用标准六类行为比例；
- 优先持续5分钟；
- 测试前按接口QPS和持续时间校验任务、邮件、好友地块等一次性状态数量；
- 如果当前夹具暂时无法支撑5分钟，则先采用3轮×30秒，报告中明确写为阶段限制，不伪装成长稳结果。

滚动更新、弱网和重连作为加分项单独演示，不塞进主容量模型。

## 6. 为什么容量阶梯使用30秒

这个游戏包含领取任务、领取邮件和偷菜等会消费状态的行为。如果不重置数据，后半段会大量返回“已领取”或“不可偷取”，测到的是数据耗尽，不是服务器性能。

30秒阶梯的好处是：

- 每一档使用相同、合法的数据起点；
- 可以快速找到性能拐点；
- 每档之间不会互相污染；
- 候选档通过三次独立重复排除偶然性。

30秒用于寻找容量，不替代规划点稳定性测试。答辩时要主动区分这两个目的。

## 7. 稳定QPS怎么判定

在没有正式产品 SLA 前，采用容易解释的工程标准：

| 指标 | 通过标准 |
|---|---:|
| 系统错误率 | ≤0.1% |
| 实际完成QPS | ≥目标QPS的99.5% |
| 整体P90 | ≤100ms |
| 整体P99 | ≤250ms |
| TaskClaim P95 | ≤500ms |
| MailClaim P95 | ≤500ms |
| 停止发压后的排空 | ≤1秒 |
| journal lag/pending | 排空后回到0 |

Avg只记录，不作为单独门槛。`Avg约50ms、P90约100ms、P99约200ms`是期待的稳定线形态，不要求三个数字同时命中。

稳定 QPS 定义：

> 相同资源、相同模型、不同随机种子的三轮测试全部通过，并且没有持续增长的队列或存储积压时，最高通过档就是稳定QPS；它上面的第一个失败档是容量边界。

## 8. 从单机结果推导容量

假设单个固定资源单元测得稳定 QPS 为 `S`，生产只使用70%：

```text
单元规划QPS = S × 70%
QPS容量单元数 = ceil(200,000 / 单元规划QPS)
```

当前6,800 QPS结果来自旧 `normal-v1` 权重，只用于演算；60次/会话的新模型复测后必须替换 `S`。暂用 `S = 6,800`：

```text
单元规划QPS = 6,800 × 70% = 4,760
QPS容量单元数 = ceil(200,000 / 4,760) = 43
```

但43只是业务吞吐计算下限。最终部署不能只看QPS，还必须看连接和Actor：

```text
Gateway数量 = ceil(峰值连接数 / 单Gateway安全连接数)
Farm数量 = max(QPS约束, 驻留Actor约束)
```

以 Farm Actor 上限20,000、规划使用70%为例，每实例按14,000个Actor规划：

```text
仅400万在线Actor就需要
ceil(4,000,000 / 14,000) = 286个Farm
```

按历史调用放大系数和单服务基准暂算，各服务规划值如下；这些数字用于说明算法，不能替代新模型复测：

| 服务 | 暂算规划值 | 主约束 |
|---|---:|---|
| Gateway | 411 | 400万连接，单实例15,000连接按65%规划 |
| Farm | 至少286 | 400万在线Actor，尚未计离线好友和会话尾部 |
| Social | 暂算6 | 历史0.3537次Social调用/业务请求、单实例20,000 QPS按70%规划 |
| MySQL | 暂算78主 | 历史SQL放大和1.5事务/慢查询余量 |
| Redis | 暂算10主 | 历史Redis命令放大和混合吞吐 |

无状态服务按3个可用区并要求容忍丢失1区时，使用 `3 × ceil(基础规划值 / 2)`：Gateway暂算618、Farm至少429、Social暂算9。MySQL和Redis按每个主分片至少配置1个跨可用区副本，分别暂算78主+78副本、10主+10副本。

因此本项目的关键结论是：43只是整套被测拓扑的业务吞吐等效下限，不是每个服务都部署43个实例。Gateway主要受连接约束，Farm主要受Actor约束，Social和存储层必须用新模型实际放大系数独立计算。完整公式和参数来源见一页答辩稿第4节。

## 10. 建议答辩讲稿

可以直接按下面的话讲：

> 我没有把3000万DAU直接当成QPS，而是先换算会话和在线人数。假设每人每天登录两次、平均在线20分钟，用户主要集中在每天10个小时内活跃，活跃时段峰值是平均值的2倍，得到峰值约400万在线用户和每秒3333次会话进入。公开资料能够说明深度经营、社交游戏存在较长会话，但没有直接给出每分钟后端请求数，所以我把它明确作为工程假设：合理区间是每分钟2到4次，只取中间值每分钟3次作为唯一容量口径。一次20分钟会话产生60次业务请求，因此全站峰值为20万业务QPS。
>
> 压测时我不要求一台机器承担全站流量，而是固定资源拓扑和1.5万条WebSocket，保持六类行为比例不变，通过开环阶梯压力找到单容量单元的稳定QPS。稳定点要求三轮全部通过，同时满足错误率、P90、P99、Claim长尾和日志排空标准，再按70%利用率用于容量规划。
>
> 单接口压测只说明接口自己的上限，混合压测还会暴露接口之间共享Actor、投影和数据库时的相互干扰。本项目最初的秒级长尾就是通过混合压测发现的，所以最终容量结论以混合稳定QPS为准，而不是把各接口单测QPS相加。

## 11. 被追问时的简短回答

**为什么这些行为比例可信？**  
它们来自现有31接口模型和产品流程的归并，公式、每会话次数和接口映射全部保留；由于没有生产埋点，明确标记为基线假设，上线后替换输入。

**为什么不是直接压20万QPS？**  
20万是全站峰值，单机K3s验证的是一个固定容量单元。先测单元稳定QPS，再结合连接、Actor和存储约束计算实例数。

**为什么不用单接口测试结果？**  
单接口没有共享资源干扰。混合测试才能暴露TaskClaim占用投影通道后拖慢普通农场请求的问题。

**为什么每档只有30秒？**  
容量阶梯需要每档处于相同合法状态，30秒加三轮独立重置用于寻找拐点；另外在70%规划点做稳定性测试，两者目的不同。

**为什么不用Avg做门槛？**  
Avg会被大量快速读接口拉低，掩盖少量用户的长尾。用户体验和系统排队更应该看P90、P99和Claim P95。
