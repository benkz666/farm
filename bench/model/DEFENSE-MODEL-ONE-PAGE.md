# 3000万 DAU 容量模型（一页答辩稿）

> **口径提示：**本文第2节之后保留的是上一轮答辩摘要，不再作为正式容量结论。当前实验设置、外推公式、基础规划、容灾规划和部署策略，统一以`CAPACITY-ESTIMATION-MODEL.md`第七至第十三节为准；不要混用本文后续的旧实例数。

## 1. 从DAU推到峰值负载

公开假设：

```text
DAU = 3000万
每人每天平均会话 = 2次
平均在线 = 20分钟
每日主要活跃窗口 = 10小时
活跃窗口内峰值系数 = 2
在线期间平均业务操作频率 = 5次/分钟
```

峰值会话到达：

```text
3000万 × 2 / (10 × 3600) × 2 = 3333.33次会话/秒
```

峰值在线与WebSocket连接：

```text
3333.33 × 20 × 60 = 400万
```

一次20分钟会话平均产生 `20 × 5 = 100` 个业务请求。三类用户加权后，把它
分成六类行为：

| 行为 | 每会话请求数 | 占比 | 主要接口 |
| ---- | -----------: | ---: | -------- |
| 进入与同步 | 10 | 10% | EnterSelf、EnterFriend、Sync |
| 本地农场 | 32 | 32% | 翻地、清理、播种、浇水、收获等 |
| 好友与跨农场 | 27 | 27% | 好友列表、进入好友、帮忙、偷菜等 |
| 任务 | 12 | 12% | TaskList、TaskClaim |
| 邮件 | 8 | 8% | MailList、MailRead、MailClaim、MailDelete |
| 商店、宠物与图鉴 | 11 | 11% | Buy、Sell、Pet、Codex |
| 合计 | 100 | 100% | 31个常用接口 |

因此峰值业务负载为：

```text
3333.33 × 100 = 333,333.33 QPS，约33.3万QPS
```

Ping/Pong、登录、握手和主动推送单独计算，不能与业务QPS直接相加。其中
400万连接按30秒心跳，对应Ping 13.33万/s、Pong 13.33万/s。

## 2. 混合压测怎么做

固定测试拓扑为 `Gateway 3 : Farm 1 : Social 1 : MySQL 1 : Redis 1`：

```text
每档重置合法账号和Journal
→ 重启业务进程并静置60秒（A窗口）
→ 建立连接和Actor并保持45秒（B窗口）
→ 按31接口权重开环发压30秒（C窗口）
→ 停压观察后台恢复60秒（D窗口）
```

3,000、5,000、7,000 QPS用来测非饱和资源成本；15,000 QPS用来做一轮
接口级SLO认证；再用相同Journal写强度的可重复写模型跑10分钟，验证后台链路
不会持续欠账；最后在相同总资源下把Gateway从3×2C拆成6×1C，测拓扑误差。

## 3. 什么叫通过

按31个接口分别判断，正式硬SLO是：

```text
P90 < 300ms
P99 < 500ms
技术错误率 ≤ 0.1%
```

`Avg≈50ms、P90≈100ms、P99≈200ms`只是理想线，不是淘汰线。本轮按“一轮
通过即可”的简化口径，15,000 QPS发送450,000个请求、全部成功，整体Avg
12.69ms、P90 19.91ms、P99 201.52ms；31个接口全部通过，最差接口P90
34.32ms，最差接口P99 306.95ms。

十分钟写链路发送9,000,000个请求，错误率0.01069%；Journal约10,829.68条/s，
Projection约10,830.87条/s，停压后4.376秒清空，最终积压和lag都为0。

## 4. 容量不是简单复制“15,000 QPS一套”

资源成本用所有副本的实际用量求和，并用A/B/C差分扣掉固定、连接和Actor成本。
最终每个服务分别计算：

```text
CPU约束
内存约束
已验证单实例业务密度约束
Gateway连接约束 / Farm Actor约束
MySQL磁盘约束 / Redis数据集约束
```

最后取最大值。实验实例配比和单实例资源仍会影响缓存、连接池、Actor路由和批处理，
所以不能说影响被完全消除。本轮用“非饱和档 + 聚合资源 + 等总资源拓扑交叉取大值
+ 水平扩展效率折扣”控制这种误差；Go服务折扣取0.90，MySQL/Redis取0.85。

本轮峰值Farm Actor工作集：

```text
400万在线
+ (3333.33新会话/s + 17000好友进入/s × 50%) × 120秒
= 542万Actor
```

所以Gateway最终由连接决定，Farm由Actor决定，而不是由每千QPS CPU决定。

## 5. 最终部署建议

基础容量不考虑容灾：

| 服务 | 实例/可写主分片 | 单实例规格 | 主约束 |
| ---- | --------------: | ---------- | ------ |
| Gateway | 353 | 2C/2GiB | 400万连接 |
| Farm | 431 | 1C/2GiB | 542万Actor |
| Social | 23 | 2C/1GiB | CPU、已验证密度 |
| MySQL | 29个主分片 | 8C/16GiB/1TiB可用盘 | CPU |
| Redis | 26个主分片 | 4C/4GiB，maxmemory 2GiB | CPU |
| 合计 | — | **1,519核/2,159GiB** | — |

三可用区、任一区故障后仍承载完整峰值的容灾版本：

| 服务 | 容灾实例/总副本 | 资源合计 |
| ---- | --------------: | -------: |
| Gateway | 530 | 1,060核/1,060GiB |
| Farm | 647 | 647核/1,294GiB |
| Social | 35 | 70核/35GiB |
| MySQL | 87，即29分片×3副本 | 696核/1,392GiB |
| Redis | 78，即26分片×3副本 | 312核/312GiB |
| 合计 | — | **2,785核/4,093GiB** |

MySQL和Redis数量是可写主分片，普通副本不增加主写容量；应用必须按UID做分片
路由，不能让数百个应用Pod各自向所有数据分片建立完整连接池。三千万注册账号
只是从DAU代入的磁盘下界，正式上线前应替换为真实账号、行为埋点和大规模水平
扩展效率。

完整公式、31接口结果和证据文件见
[`CAPACITY-ESTIMATION-MODEL.md`](CAPACITY-ESTIMATION-MODEL.md)。
