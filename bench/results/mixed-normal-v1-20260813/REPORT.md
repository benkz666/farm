# 3000 万 DAU 混合压测与容量估算报告

测试日期：2026-08-13  
行为模型：`normal-v1`  
容量单位：Gateway/Farm/Social 均为 1 CPU、1 GiB；MySQL 为 2 CPU、4 GiB；Redis 为 1 CPU、1 GiB。

## 1. 结论

1. Gateway 轻量化改造没有导致本次性能下降。完整模型在去掉 `TaskClaim` 和
   `MailClaim` 后，3 Gateway + 1 Farm 可稳定完成 5,000 QPS，错误为 0，P95 为
   23.74 ms；这个档位只是通过点，不是测得的上限。
2. 当前完整混合流量的单组安全点是 500 QPS：15,000/15,000 成功，P95 3.81 ms，
   P99 52.45 ms。到 1,000 QPS 时出现非线性雪崩：失败 129/30,000，P95 1.73 s，
   任务领取 P95 3.74 s。
3. 根因在 Farm 的一致性屏障和共享流工作槽。现场 135 个 Actor 等待
   `WaitUIDProjected`，其中 TaskClaim 117 个、MailClaim 18 个；它们占住了
   192 个 Gateway→Farm 工作槽中的大部分，导致其他 UID 的快请求队头阻塞。
   10,364 个 Actor 当时处于空闲，Gateway/Farm CPU 也没有打满。
4. 把投影器从 4 增加到 8 后，1,000 QPS 仍失败，P95 1.75 s，说明单纯增加投影
   并发不能修复阻塞式工作槽耦合。
5. 按本报告的无埋点假设模型，生产建议容量是 Gateway 312、Farm 264、Social 3，
   Gateway:Farm 约为 1.18:1，不应继续硬编码为 3:1。Gateway 的 312 个实例主要
   由 300 万 WebSocket 连接的内存约束决定，按业务 CPU 只需要 74 个；因此
   “Gateway 实例多”不代表 Gateway 的业务逻辑比 Farm 重。

这些副本是 3000 万 DAU 的全局容量单元，不是在当前单机 k3s 上实际启动的 Pod
数量。生产需要按地域和 UID 分片拆分；当前 k3s 用来验证单容量单元和瓶颈即可。

## 2. 用户行为模型

### 2.1 人口与峰值

| 输入 | 假设 |
|---|---:|
| DAU | 30,000,000 |
| 每 DAU 每日会话 | 2 次 |
| 平均会话 | 20 分钟 |
| 日均到峰值系数 | 3.6 |
| 峰值 PCU | 3,000,000 |
| 峰值新会话 | 2,500/s |
| WebSocket 握手（含 10% 重连） | 2,750/s |
| Ping / Pong | 各 100,000/s |

四类会话为快速玩家 35%、日常玩家 40%、社交玩家 20%、重度玩家 5%。完整 31 个
可执行操作及每秒次数在 `bench/model/user-behavior.normal-v1.json` 中。模型换算得到：

| 系统负载 | 峰值 |
|---|---:|
| 可执行混合业务请求 | 69,264.65 QPS |
| 独立一次性社交写请求 | 630.27 QPS |
| 总前端业务请求 | 69,894.92 QPS |
| Farm 前端请求 | 59,294.39 QPS |
| Social 调用（含跨农场鉴权） | 24,500.53 QPS |

### 2.2 发压比例

请求按行为模型的 `reference_qps / 69,264.65` 做全局加权随机选择，但总到达率由
开环调度器严格控制，不会因为服务变慢而自动降压。15,000 条连接分成：

- 50% 自己农场账号；
- 20% 访问好友农场账号；
- 30% 社交/被访问账号。

每条连接内部串行发送，保持 WebSocket 的客户端序号和同账号命令顺序；不同账号
并行。状态写操作使用不同合法地块，任务和邮件领取使用一次性夹具。队列满时记为
压测到达丢弃 `-2`，WebSocket 交换超时记为 `-1`，业务错误码单独汇总。

这个驱动验证的是峰值稳定期的聚合比例。上线后应把模型中的假设替换为 P95 日的
埋点：会话时长、按钮次数、好友访问率、接口错误码、每 UID 热点度和重连率。

## 3. 测试方法和 SLO

每个完整档位执行以下流程：等待 Farm 写日志 pending/lag 清零；重置 15,000 个
专用账号；清空 Actor 热状态；并发建立 15,000 条 WebSocket；预热自己和好友
农场；等待 2 秒；在测量窗口内开环按比例发压；最后排空队列并单独记录排空时间。

通过标准：整体错误率不高于 0.1%，整体 P95 不高于 50 ms，P99 不高于 250 ms，
领取类 P95 不高于 500 ms，测量后排空不超过 1 秒。

## 4. 实测结果

### 4.1 完整行为模型

| 目标 QPS | 成功/发送 | 错误率 | P95 | P99 | 排空 | 结论 |
|---:|---:|---:|---:|---:|---:|---|
| 250 | 7,500/7,500 | 0 | 3.67 ms | 7.43 ms | 37 ms | 通过 |
| 500 | 15,000/15,000 | 0 | 3.81 ms | 52.45 ms | 37 ms | 通过 |
| 1,000 | 29,871/30,000 | 0.43% | 1,726.92 ms | 3,659.17 ms | 1,265 ms | 失败 |

500 QPS 时 TaskClaim/MailClaim P95 分别为 241.31/231.15 ms；1,000 QPS 时升为
3,736.68/3,591.95 ms。成功率之前，延迟已经先越过 SLO。

### 4.2 瓶颈隔离

| 场景 | 结果 |
|---|---|
| 去掉 TaskClaim/MailClaim，5,000 QPS | 50,000/50,000 成功；P95 23.74 ms；P99 44.50 ms |
| 投影器 4→8，完整 1,000 QPS | 29,880/30,000 成功；P95 1.75 s；无实质改善 |
| 单 Gateway 15,000 连接 + 500 Ping/s | 15,000/15,000 成功；P95 0.13 ms |
| 单 Social + 真实 MySQL，20,000 QPS | 399,960/399,960 成功；P95 3.65 ms |

因此旧的“每接口 6,000+ QPS”与本次结果不矛盾：单接口测试没有把快操作排在
阻塞式领取操作后面。混合测试暴露的是接口之间的干扰，而不是某个快接口自身容量。

### 4.3 存储层

完整 500 QPS 通过档扣除空闲消耗后，每个前端业务请求平均产生 3.5896 条 MySQL
statement 和 10.4941 条 Redis command。

MySQL 使用项目实际的 `friendship(uid_lo, uid_hi)` 索引查询做只读边界：2 CPU、
4 GiB 在 20,000 QPS 全成功，P95 0.43 ms；40,000 目标档实际只能完成
22,894 QPS，失败 4,203，P95 189.32 ms。规划上限取通过档 20,000，不取失败档。

Redis 使用专用 DB 15、100 并发、pipeline 16：SET 304,599 ops/s，GET 450,450
ops/s；按 50% 读写的调和吞吐为 363,438 ops/s。测试后 DB 15 的 631,850 个专用
基准 key 已全部清空，业务 DB 0 未修改。

## 5. 容量计算

### 5.1 Gateway

连接约束：`ceil(3,000,000 / (15,000 × 65%)) = 308`。  
CPU 约束：`ceil(69,894.92 × 0.7381 ms / (1,000 × 70%)) = 74`。  
取较大值 308，再加故障域余量并按 3 个域取整，建议 **312 个 Gateway**。

### 5.2 Farm

驻留 Actor 估算：

`3,000,000 PCU + 2,500 × 120s 会话尾部 + 5,725 × 120s × 50% 离线好友`

得到 3,643,500 个 Actor。单实例 `ACTOR_MAX_RESIDENT=20,000`，按 70% 占用为
14,000，因此需要 261 个。

完整混合 SLO 约束：`ceil(69,264.65 / (500 × 70%)) = 198`。  
CPU 约束：`ceil(69,894.92 × 0.716 ms / (1,000 × 70%)) = 72`。  
取较大值 261，加故障域余量并取整，建议 **264 个 Farm**。

Farm 不能只靠 CPU HPA；Actor 数量、write journal lag、claim barrier waiters 必须加入
扩缩容指标，而且 UID 分片迁移不适合在峰值时临时完成。

### 5.3 Social

前端社交 10,600.53 QPS，加跨农场鉴权 13,900 QPS，共 24,500.53 QPS。
单实例通过值 20,000，按 70% 为 14,000，基础需要 2 个；为 N+1 建议
**3 个 Social**。

### 5.4 MySQL

峰值 SQL：`69,894.92 × 3.5896 + 2,500 × 2` = **255,898 statements/s**。
单主分片按 `20,000 × 70% = 14,000/s`，只读等价下限为 19 个主分片。考虑 Farm
批量写、事务、checkpoint 和测试未覆盖的慢查询，乘 1.5 复杂度系数，建议
**28 个主分片 + 28 个只读/热备副本**。

这不是把当前 StatefulSet 简单扩为 28。应先按 UID 拆 Farm/Task/Mail 数据，Social
关系数据单独分库，并通过分片路由层管理；跨分片事务需要异步事件或补偿机制。

### 5.5 Redis

业务命令约 `69,894.92 × 10.4941 = 733,482/s`，再加会话和租约 300,000/s，
总计 **1,033,482 commands/s**。单主分片按 `363,438 × 70% = 254,407/s`，需要
5 个主分片。建议 **5 主 + 5 从** 的 Redis Cluster，并至少从 4 GiB/Pod 起步；
真实埋点补齐后再按 key 数、平均 value 和碎片率校核内存。

## 6. 建议部署值

| 组件 | 计算下限 | 建议值 | 主约束 |
|---|---:|---:|---|
| Gateway 1C1Gi | 308 | 312 | 300 万 WebSocket 连接内存 |
| Farm 1C1Gi | 261 | 264 | 驻留 Actor；其次是当前 claim 屏障 |
| Social 1C1Gi | 2 | 3 | 24,500/s 社交及跨农场鉴权，N+1 |
| MySQL 2C4Gi | 19 主 | 28 主 + 28 从 | SQL 放大与写事务复杂度 |
| Redis | 5 主 | 5 主 + 5 从 | 约 103 万 command/s |

建议 Gateway:Farm 为 `312:264 ≈ 1.18:1`。这个比例来自 PCU、Actor、混合 QPS、
存储和安全余量共同计算，不能由某一个热接口的最高 QPS反推。

## 7. 必须修复和复测的事项

1. P0：让投影屏障操作不再阻塞通用 `ExecuteBatchStream` 分片工作槽。可选方案是
   异步提交 Actor 请求并在完成通道回包，或为需要屏障的命令提供隔离执行通道；
   仍需保持同 UID Actor 顺序和 claim 前的持久化屏障。
2. P0：为 `WaitUIDProjected` 增加等待时长、等待 UID 数和命令类型指标；当前只有
   journal lag，无法在告警时直接定位 claim 堵塞。
3. P1：Farm 滚动后，Gateway→Farm 长流曾在预热阶段连续返回 1001；Gateway
   readiness 应验证可用 Farm 流，流断开后需要稳定重连，发布流程需加入端到端探针。
4. P1：修复后重复 500/1,000/2,000/5,000 QPS 完整阶梯和 30 分钟稳定性测试。
   在修复完成前，不应把“无 claim 的 5,000 QPS”作为生产完整容量。
5. P1：上线埋点后用 P95 日数据替换行为假设，并按同一脚本重新计算。

## 8. 复现

容量计算：

```bash
python3 bench/api/mixed_capacity.py \
  --model bench/model/user-behavior.normal-v1.json \
  --benchmarks bench/results/mixed-normal-v1-20260813/benchmark-summary.json \
  --output bench/results/mixed-normal-v1-20260813/capacity-result.json
```

混合压测驱动支持 `-behavior-model` 和 `-exclude-operations`。正式档应直连三个
Gateway Pod IP，避免单个 Service 目的地址在负载 Pod 上耗尽临时端口；每档必须
重新准备合法夹具，且 `FARM_TIME_PROFILE` 与夹具保持一致。
