# 经典农场模块隔离压测与容量规划报告

## 摘要

本轮采用方案 A：把 3000 万 DAU 峰值模型等比例缩小为 3% 标准容量单元，分别验证 Gateway、Farm 和 Social，再依据实测 CPU、内存、连接和 Actor 成本外推生产资源。受单机条件限制，本报告不声称直接压出了 33.3 万 QPS 和 400 万连接；结论是用于预算和部署设计的一阶容量估算。

| 项目 | 结果 |
|---|---:|
| 生产峰值业务负载 | 333,333.33 QPS |
| 生产峰值长连接 | 4,000,000 |
| 生产 Farm Actor 工作集 | 约 5,420,000 |
| 标准单元比例 | 3% |
| Gateway 单元 | 10,000 业务 QPS、120,000 连接、30 秒心跳、102 次/秒新建或重连 |
| Farm 单元 | 8,570 QPS、162,603 Actor |
| Social 单元 | 3,210 QPS，80% 热用户、20% 冷用户 |
| SLO | 各接口 P90 < 300 ms、P99 < 500 ms、技术错误率 ≤ 0.1% |
| 测试结论 | 三个模块的标准单元全部通过，业务请求技术错误率均为 0 |
| 生产基础逻辑资源 | 约 389.6 核 CPU、642.9 GiB 内存（均已按 70% 水位规划） |
| 基础部署建议 | 107 个服务实例或数据节点，438 核 CPU、814 GiB 内存 |
| 三可用区容灾建议 | 175 个服务实例或数据节点，792 核 CPU、1,378 GiB 内存 |

## 一、工作负载与模块映射

### 1.1 生产模型

工作负载模型采用以下公开假设：3000 万 DAU、每人每天 2 次会话、主要活跃窗口 10 小时、峰值系数 2、平均在线 20 分钟、平均每分钟 5 次业务操作。

由此得到：

$$
\lambda=\frac{30{,}000{,}000\times2}{10\times3600}\times2
=3{,}333.33\ \text{次会话/秒}
$$

$$
C=3{,}333.33\times20\times60\approx4{,}000{,}000\ \text{在线连接}
$$

$$
Q=3{,}333.33\times100\approx333{,}333.33\ \text{业务QPS}
$$

心跳周期为 30 秒，因此生产峰值约有 133,333 Ping/s 和 133,333 Pong/s。每分钟 0.1% 的连接重连，对应约 66.67 次重连/s；与正常会话进入合计约 3,400 次建连/s。

### 1.2 标准容量单元

标准单元取生产模型的 3%，三个状态维度使用相同缩放比例：

| 维度 | 生产目标 | 标准单元 | 外推倍数 $K$ |
|---|---:|---:|---:|
| 业务 QPS | 333,333.33 | 10,000 | 33.3333 |
| WebSocket 连接 | 4,000,000 | 120,000 | 33.3333 |
| Farm Actor | 5,420,000 | 162,600 | 33.3333 |

模块负载不是把 10,000 QPS 原样压给每个服务，而是按真实调用链汇总：

| 模块 | 生产目标 | 标准单元 | 组成 |
|---|---:|---:|---|
| Gateway | 333,333.33 QPS | 10,000 QPS | 全部 31 个客户端业务接口 |
| Farm | 285,666.67 QPS | 8,570 QPS | 27 个农场、任务、邮件、商店、宠物和图鉴接口 |
| Social | 107,000 QPS | 3,210 QPS | 4 个直接社交接口及 5 类业务触发的关系校验 |

完整逐接口调用映射见 [MODULE-LOAD-MAPPING.md](./MODULE-LOAD-MAPPING.md)。MySQL SQL TPS 和 Redis 命令 QPS 不预设静态倍数，而是在真实 Farm/Social 链路中测量，因为缓存命中、批量提交和投影合并会改变每个业务请求产生的下游操作数。

### 2.2 模块隔离拓扑

| 被测模块 | 请求路径 | 被测实例配额 | 说明 |
|---|---|---:|---|
| Gateway | 3 个发压器 → 真实 Gateway → Mock Farm/Social → 真实 Redis | 1 × 5C/12GiB | Mock 为 2C/512MiB，协议与响应结构保持一致 |
| Farm | 3 个发压器 → Gateway 传输层 → 真实 Farm → 真实 MySQL/Redis | Farm 1 × 5C/10GiB | 保留 27 接口、Actor、Journal、Projection 和异步落库；只统计 Farm 自身资源 |

Farm 本轮保留 Gateway 传输层，是为了复用同一套合法的 27 接口行为与状态机；Gateway 在该轮资源充足且单独计量，因此不会把 Gateway 资源计入 Farm。主动推送链路也在真实 Farm 轮次中得到覆盖。若要取得完全绕过 Gateway 的 Farm 数据，需要再实现与 27 个客户端操作等价的内部混合协议，本轮未以一个语义较弱的单操作回放代替它。

### 2.3 采样窗口

每轮按以下窗口采样：

| 窗口 | 含义 | 用途 |
|---|---|---|
| A | 服务空载 | 固定 CPU 与内存基线 |
| B | 连接、心跳和 Actor 已驻留，未发业务 | 状态成本 |
| C | 按目标行为比例发送业务请求 | 逐接口 SLO 与前台资源 |
| D | 停止前台请求，等待异步任务排空 | 把 Journal/Projection 等响应后工作计入容量 |

接口时延只统计成功响应，不把异步落库时间算入前台响应；但异步落库消耗的 CPU 和内存通过 D 窗口计入容量。失败请求单独进入技术错误率，避免快速失败把延迟数据“优化”下来。

### 2.4 测试工具修正

正式数据产生前修正了四类压测工具问题：Mock 延迟串行执行造成的假吞吐瓶颈、心跳在连接预热完成后才启动、辅助建连账号与常驻连接账号重叠导致会话互踢，以及模块隔离判定器错误要求未参与测试的接口必须出现。Social 结果生成后的时间戳字段读取错误也已修正，仅补采监控和 SLO，没有重复业务负载。上述错误轮次均未进入本报告。

## 四、从标准单元外推资源

### 4.1 计算方法

设 $K=33.3333$，服务 $s$ 在 A 窗口的固定 CPU 为 $C_{s,A}$，B 相对 A 的状态 CPU 增量为 $\Delta C_{s,state}$，本轮请求在 C 与 D 窗口消耗的完整业务 CPU 为 $C_{s,biz}$。生产原始需求与 70% 规划需求为：

$$
C_{s,raw}=C_{s,A}+K(\Delta C_{s,state}+C_{s,biz})
$$

$$
C_{s,plan}=\frac{C_{s,raw}}{0.7}
$$

内存分别使用固定、状态和负载峰值增量：

$$
M_{s,raw}=M_{s,A}+K(\Delta M_{s,state}+\Delta M_{s,load})
$$

$$
M_{s,plan}=\frac{M_{s,raw}}{0.7}
$$

CPU 和内存独立计算，最后才选择实例规格。MySQL 的 Farm、Social 增量相加且固定基线只算一次。Redis CPU 使用 Farm 整链路成本，再补 Social 以及对应 Gateway 路由成本，避免把 120,000 条 Gateway 连接重复计算；Redis 内存按单元末尾实际数据集加固定开销外推。

|---|---:|---:|---:|---:|---:|---:|---:|
| Gateway | 2.697 核 | 5,639.7 MiB | 1,726.1 MiB | 89.90 核 | 128.44 核 | 239.78 GiB | 342.55 GiB |

Gateway 每实例约承载 117,647 条连接，低于本轮实测的 120,000；Farm 每实例约承载 159,412 个 Actor，低于本轮实测的 162,603。CPU、内存和状态密度分别计算后取最大值，避免再次把资源绑定到测试时的单实例配额。

### 5.2 三可用区容灾规划

目标定义为任意一个可用区失效后，剩余两个可用区仍不少于基础容量。无状态与 Actor 服务按基础数量的 1.5 倍规划；MySQL 使用一主两副本且每个节点具备接管规格；Redis 每个主分片配置一个跨可用区副本。

| 服务 | 容灾部署 | 单实例规格 | 总 CPU | 总内存 |
|---|---|---:|---:|---:|
| Gateway | **51 个，17/17/17** | 4C/12GiB | 204 核 | 612 GiB |
| Farm | **51 个，17/17/17** | 4C/8GiB | 204 核 | 408 GiB |
| Social | **18 个，6/6/6** | 2C/1GiB | 36 核 | 18 GiB |
| MySQL | **3 个，一主两副本，每区 1 个** | 64C/96GiB | 192 核 | 288 GiB |
| Redis | **26 主 + 26 副，主副跨区** | 3C/1GiB | 156 核 | 52 GiB |
| **合计** | **175 个实例或数据节点** | — | **792 核** | **1,378 GiB** |

### 5.3 运行策略

- Gateway 通过四层负载均衡分发连接；扩缩容同时看 CPU、内存和连接数，更新时先停止接收新连接，再排空旧连接。
- Farm 按玩家标识稳定路由；扩缩容同时看 CPU、内存、Actor 数、邮箱深度和 Journal/Projection 积压，缩容前迁移或自然回收 Actor。
- Social 无状态水平扩展，主要依据 CPU、P99 和缓存命中率。
- MySQL 的单节点 64C 结果未在当前 32 逻辑 CPU 机器上直接验证；生产前应在目标数据库规格上验证写吞吐、IOPS、提交时延和复制延迟。
- Redis 以命令 QPS 和最热分片 CPU 扩容，不能把 75 核简单配置给一个 Redis 进程；需要 26 个主分片并监控热点与数据倾斜。

## 六、结论与边界

本轮可以证明：在 3% 标准单元下，Gateway、Farm 和 Social 均能按目标行为比例兑现吞吐，并满足逐接口 SLO；连接、Actor 和业务成本可以从监控窗口分离，CPU 与内存也可以独立外推后再换算实例。

本轮不能证明 33.3 万 QPS、400 万连接在真实多节点环境中必然线性扩展。主要剩余风险为：跨节点路由与负载不均、MySQL 大规格纵向扩展效率、Redis 分片热点、完整生产数据集大小、数小时稳定运行、可用区故障切换，以及尚未由真实埋点校准的用户行为比例。因此，基础和容灾方案适合预算与架构评审；正式采购和上线前仍需在目标云环境做一次缩小范围的多节点验收与长稳测试。

测试结束后已恢复 Gateway 的真实 Farm/Social 下游、单实例业务拓扑及 10k 资源配额，并删除临时 Mock。原 K6 镜像标签已不在节点本地且拉取策略为 `Never`，因此 K6 保留为本轮已验证的兼容镜像；它不属于生产服务拓扑。
