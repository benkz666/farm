## 1. 这份估算最重要的部分是假设，不是数字

容量估算的结论天然是不精确的。真正决定它有没有价值的，是假设是否被明确写出、是否可被质疑、是否可被实测替换。因此本文把假设放在最前面。

### 1.1 需求侧假设

| 假设 | 取值 | 依据 | 如果错了会怎样 |
| --- | ---: | --- | --- |
| 人均日登录次数 | 4 | 农场是碎片化玩法，早中晚各一次加一次随机 | 直接线性影响并发与 QPS |
| 单次会话时长 | 5 分钟 | 收菜 + 逛好友的典型时长 | 直接线性影响并发 |
| 单次会话操作数 | 30 | 与作物循环交叉验证，见 1.3 | 直接线性影响 QPS，不影响并发 |
| 晚高峰并发系数 | 4.0 | 国内休闲游戏经验值 | 影响 PCU，进而影响网关台数 |
| 峰值 QPS 系数 | 5.0 | 略高于并发系数，高峰期操作更密集 | 影响逻辑层台数 |
| 写操作占比 | 40% | 种植循环的动作绝大多数是写 | 影响 MySQL 分片数 |
| 房间平均订阅者 | 1.3 | 绝大多数时候农场里只有主人自己 | 影响广播量与网关带宽 |
| 注册用户 / DAU | 4 | 行业经验值 | 影响存储总量 |

### 1.2 单机能力假设

这一组是**必须由压测实测替换**的。当前值是保守的行业经验值，第 4 章会反推出压测必须达到的通过线。

| 假设 | 取值 | 压测中对应的验证项 |
| --- | ---: | --- |
| 单网关连接数 | 250,000 | 建连压测，观察 RSS 斜率 |
| 单连接内存 | 4,608 B | 同上 |
| 单逻辑服 QPS | 30,000 | 阶梯加压找 P99 拐点 |
| write-behind 合并率 | 5:1 | 见 3.5 节的重要警告 |
| MySQL 单实例写 TPS | 3,000 | 独立压测 |
| Redis 单用户缓存 | 8 KB | 实测采样 |

### 1.3 一个交叉验证

「单次会话 5 分钟、30 次操作」和「峰值 QPS 20.8 万、PCU 166.7 万」这两组数字必须自洽。脚本用人均操作频率做交叉验证：

```text
峰值人均操作频率 = 20.8 万 / 166.7 万 = 0.125 次/秒 = 每 8 秒一次操作
```

每 8 秒点一下，对于「进农场看一眼、收几块地、逛两个好友」的节奏是合理的。如果这个数字算出来是每秒 3 次或每分钟 1 次，说明会话时长和操作数两个假设互相矛盾。脚本对此有断言。

## 2. 推导链

### 2.1 并发

```text
日总在线时长 = 3000 万 × 4 次 × 5 分钟 = 1,000 万 小时
全天平均并发 = 1000 万 / 24     = 41.7 万
峰值并发     = 41.7 万 × 4      = 166.7 万
PCU 设计值   = 166.7 万 × 1.2   = 200 万
```

PCU / DAU = 5.6%，落在休闲游戏 3%—20% 的典型区间内。

### 2.2 请求与消息

```text
日请求总数   = 3000 万 × 4 × 30  = 36.0 亿
全天平均 QPS = 36 亿 / 86400     = 4.2 万
峰值 QPS     = 4.2 万 × 5        = 20.8 万
QPS 设计值   = 20.8 万 × 1.2     = 25.0 万
峰值写 QPS   = 20.8 万 × 40%     = 8.3 万

出向 · 应答 = 20.8 万 msg/s
出向 · 广播 = 8.3 万 × 1.3 = 10.8 万 msg/s
出向合计    = 31.7 万 msg/s → 0.63 Gbps
```

**带宽完全不是问题**，0.63 Gbps 分摊到 12 台网关，单机出向仅占 10 Gbps 网卡的 0.5%。这个结论直接来自 [architecture.md](architecture.md) 2.3 节的判断——农场不是 MMO，扇出是 O(几) 而不是 O(几百)。如果按 MMO 的扇出建模，同样的 PCU 会产生上亿 msg/s，带宽会立刻成为首要瓶颈。

### 2.3 存储

单用户数据量的逐字段拆解见 [architecture.md](architecture.md) 5.8 节，这里只列汇总：

```text
内存热数据 / 用户 = 7,172 B × 1.4（Go 开销） = 9.8 KB
落库裸数据 / 用户 = 10.4 KB（邮件按正文计）

注册用户    = 3000 万 × 4 = 1.2 亿
裸数据      = 1.16 TB
含行开销索引 = 1.16 × 2.5 = 2.90 TB
在线流水    = 36 亿 × 10% × 100 B × 7 天 = 0.23 TB
在线总存储  = 3.12 TB
```

### 2.4 MySQL 分片数

```text
峰值写 QPS（设计值）        = 10.0 万
write-behind 合并 5:1 后    = 2.0 万 TPS
按写 TPS 需要分片 = 20000 / 3000  = 7 个
按容量需要分片   = 3120 GB / 500 = 7 个
取大者 × 2 倍增长余量，向上取 2 的幂 = 16 个主分片
逻辑分片 / 物理分片 = 1024 / 16 = 64
```

**write-behind 是这里的决定性因素。** 没有它，需要的分片数是 `100000/3000 = 34` 个，向上取 2 的幂并留余量就是 128 个。合并率 5:1 把 MySQL 集群规模压掉了 8 倍。这也是为什么合并率被列为核心监控指标（[architecture.md](architecture.md) 10.1 节）。

### 2.5 机器清单

| 组件 | 台数 | 规格 | 约束来自 |
| --- | ---: | --- | --- |
| Gateway | 12 | 16C32G | 连接数（200 万 / 25 万 × 1.5 冗余） |
| FarmServer | 16 | 16C64G | CPU（25 万 QPS / 3 万 × 1.5 冗余，取 2 的幂） |
| Redis | 16 | 16C64G | 容量（229 GB，主从分离，单机 2 实例占 50% 内存） |
| MySQL | 32 | 16C64G SSD | 16 主 + 16 从 |
| 其他服务 | 26 | — | Auth 4 / Social 4 / Task 4 / Mail 4 / Kafka 6 / 运维 4 |
| **合计** | **102** | | |

FarmServer 台数取 2 的幂，是为了让 1024 个逻辑分片能均匀分配（每实例 64 个）。脚本对 `1024 % 台数 == 0` 有断言。

两个值得注意的结果：

**Actor 内存远未成为瓶颈**。260 万个活跃 Actor 共 24.3 GB，分摊到 16 台每台只有 1.74 GB，占 64 GB 机器的 2.7%。逻辑层的约束是纯 CPU。这是决策 D1 惰性推进的直接结果——不驻留的农场完全不占资源，而 3000 万 DAU 中同时驻留的只有 260 万。

**网关的连接内存也不紧张**。25 万连接 × 4.6 KB = 1.07 GB，占 32 GB 的 3.4%。但这个数字建立在「4,608 B/连接」这个假设上，而它需要专门的工程手段才能达到，见 3.1 节。

### 2.6 这份估算不能告诉你什么

诚实地列出边界，比多算几个数字更重要：

- **它不能预测热点分布**。均值假设掩盖了长尾：一个有 200 个好友的大 V 农场，其 Actor 的负载可能是均值的百倍。这只能靠 mailbox 深度监控发现
- **它不能预测行为变化**。运营活动会瞬间改变操作分布，比如「双倍偷菜日」会让跨 Actor 操作占比翻倍
- **它假设了均匀分片**。`hash(uid)` 的分布是均匀的，但活跃度不是——如果某批 uid 恰好是同一批高活跃用户，会出现分片倾斜
- **它没有建模冷启动**。晚高峰的 Actor 加载洪峰是一条独立的压力曲线，见 3.7 节

## 3. 瓶颈分析

按**压测中实际暴露的先后顺序**排列。这个顺序本身是有信息量的：它告诉你优化应该从哪里开始。

### 3.1 网关连接内存（最先暴露）

**现象**：连接数刚上到 5 万，网关 RSS 就到了 1.2 GB，继续加连接触发 OOM。

**成因**：Go 的朴素 WebSocket 实现是 goroutine-per-connection，每连接两个 goroutine（读、写）各 8 KB 栈起步，加上 `bufio.Reader` / `bufio.Writer` 各 4 KB，合计约 24 KB。5 万连接就是 1.2 GB，而且 goroutine 调度开销随连接数线性增长。

**对策**：

1. 换用基于 epoll 的库（`nbio` 或 `gnet`），去掉 per-connection goroutine，改为事件回调模型
2. 读 buffer 按需从共享池分配。农场的消息极小（入向均值 120 B），绝大多数时候连接上没有在途数据，不需要常驻 buffer
3. 写 buffer 同理，且配合 3.2 节的写合并

**量化目标**：24 KB → 4.6 KB，单机连接数 5 万 → 25 万。

**验证方法**：压测客户端只建连、只发心跳、不发业务消息，画 RSS 对连接数的曲线，斜率就是单连接内存。这是最容易做也最容易出漂亮数字的一项优化。

### 3.2 网关 CPU：TLS 与系统调用

**现象**：吞吐上到 1.5 万 QPS 时网关 CPU 先于逻辑层打满。

**成因**：常见的分析会归咎于 protobuf 序列化，但在这个系统里那不是主因——扇出只有 1.3，重复编码的浪费很小。真正的开销是**每条消息一次 TLS 加密 + 一次 write 系统调用**。31.7 万 msg/s 分摊到 12 台是每台 2.6 万次 write/s，每次 TLS record 封装加系统调用约 3—5 μs，占掉 8%—13% 的一个核心；连接数多时缓存局部性变差，实际更高。

**对策**：

1. **写合并**：同一连接上 1—2 ms 内的多条消息合并成一次 TLS record、一次 write。农场的延迟预算是 500 ms，2 ms 的合并窗口完全无感
2. **广播一次编码**：Actor 侧把 payload 编码一次，按 Gateway 分组下发 `PushBatch`（[protocol.md](protocol.md) 2.5 节）。虽然平均扇出只有 1.3，但大 V 农场房间可能有几十人，这一项在长尾上有意义
3. TLS 会话复用，避免重连时的完整握手

**验证**：监控 `编码次数 / 广播次数` 和 `write 系统调用数 / 消息数` 两个比值，理想值分别是 `1/订阅者数` 和远小于 1。

### 3.3 Actor mailbox 热点（预期中的非瓶颈）

把这一项写出来，是因为它看起来像瓶颈但实际不是，而这个判断需要有数据支撑。

**担忧**：决策 D2 把一个玩家的全部操作串行到单个 goroutine，大 V 农场同时被几十人操作时会不会排队？

**量化**：单个 Actor 处理一次操作是纯内存计算，`advance()` 约 200 ns，加上校验、提交、delta 生成，合计 3—5 μs，即单 Actor 可达 20—30 万 op/s。而一个农场即使有 30 个访客同时操作，也不过 30 op/s。**余量四个数量级。**

**结论**：不是瓶颈。但必须监控 mailbox 深度以持续确认这个判断——它是 [architecture.md](architecture.md) 10.1 节列的核心告警项。正常值恒为 0—1，持续大于 10 即说明判断失效。

### 3.4 Redis 热点 key

**现象**：`FriendList` 接口的 P99 明显高于其他接口。

**成因**：[protocol.md](protocol.md) 5.5 节的「好友农场有无可偷作物」摘要如果实现成一个全局大 hash，会成为单 key 热点。一次 `FriendList` 要读 200 个字段，而这个接口在「逛好友」路径上是高频的。

**对策**：摘要按 `hash(uid) % 1024` 拆成 1024 个小 hash；Gateway 侧对摘要加 1 秒 TTL 的本地缓存。摘要本来就是弱一致的，1 秒延迟毫无影响。

### 3.5 MySQL 写合并率（最容易得出错误结论的一项）

**这一节是全文最重要的警告。**

write-behind 合并率取决于「同一个 Actor 在一个 flush 周期内被写了几次」。而这个量**强烈依赖时间档**：

| 时间档 | 白萝卜一轮 | 30 秒 flush 周期内的地块写次数 | 表观合并率 |
| --- | ---: | ---: | ---: |
| `authentic` | 10 小时 | 约 0.008 次 | 接近 1:1（无合并） |
| `fast` | 10 分钟 | 约 0.5 次 | 约 1.5:1 |
| `bench` | 10 秒 | 约 28 次 | 约 20:1（严重虚高） |

如果用 `bench` 档压测得出「合并率 20:1」并回填进容量模型，MySQL 分片数会被低估 4 倍，上线后直接被打爆。

**正确做法**：

1. 吞吐压测用 `bench` 档（它的目的是快速跑完玩法循环）
2. **合并率必须单独在 `authentic` 或 `fast` 档测量**，或者用「按真实操作间隔建模」的机器人测量
3. 更稳妥的是把合并率当作**可调参数**而非实测值：把 flush 周期从 30 秒调到玩家真实操作间隔的量级（比如 5 分钟），用内存换写放大

这个陷阱之所以危险，是因为压测跑出来的数字看起来非常漂亮，没有任何报错。

### 3.6 Go GC

**现象**：稳态运行 10 分钟后 P99 延迟出现周期性尖刺。

**成因**：单机 16 万个 Actor，每个含 map 和 slice，堆上有数百万个对象；加上每秒数万个临时消息对象。GC 的标记阶段时间随存活对象数线性增长。

**对策**：

1. `Plot` 用值数组 `[18]Plot` 而不是 `[]*Plot`，18 块地是一整块连续内存、零指针，GC 扫描时可以整体跳过
2. 消息对象和编码 buffer 走 `sync.Pool`
3. `advance()` 做到 **0 allocs/op**——它在每个请求上都被调用，一旦分配内存，GC 压力就是 `QPS × 分配量`
4. 设置 `GOMEMLIMIT` 而不是只调 `GOGC`，前者能在内存接近上限时更平滑地加大 GC 频率

**目标**：GC pause P99 < 5 ms。

### 3.7 登录洪峰与 Actor 冷启动

**这是唯一一条 QPS 曲线与玩法 QPS 曲线不同的压力源**，必须单独压。

**量化**：晚高峰 PCU 从 41.7 万涨到 166.7 万，若涨幅集中在 10 分钟内，即 **2,083 次 Actor 冷加载/秒**。每次冷加载在 Redis 命中时是 1 次读、未命中时是 1 次 Redis miss 加 3—4 次 MySQL 查询。缓存冷的情况下这是 8,000 QPS 的 MySQL 读压力，且都是随机点查。

**对策**：

1. 同 uid 的并发加载用 `singleflight` 合并（多个访客同时进入同一个农场是常见的）
2. 加载并发限流，超出时排队而不是打穿存储
3. 高峰前预热：按前一日的活跃时段预加载 Redis

### 3.8 瓶颈优先级小结

| 顺位 | 瓶颈 | 性质 | 优化收益 |
| ---: | --- | --- | --- |
| 1 | 网关连接内存 | 硬约束，不优化就上不去 | 单机连接数 5x |
| 2 | 网关 TLS 与系统调用 | CPU | 网关吞吐 2—3x |
| 3 | Actor 内存分配与 GC | 延迟抖动 | P99 显著改善 |
| 4 | MySQL 写合并率 | 容量成本 | MySQL 集群规模 5—8x |
| 5 | 冷启动洪峰 | 可用性风险 | 避免高峰雪崩 |
| — | mailbox 串行 | 分析后确认非瓶颈 | — |
| — | 带宽 | 分析后确认非瓶颈 | — |

## 4. 压测方案

### 4.1 通过线是怎么来的

压测最容易犯的错误是「压出一个数字，然后说这个数字很大」。本项目把容量模型反过来用，先算出一个**可判定的通过线**：

```text
集群总吞吐 = 单机实测拐点 × 台数 × 折扣系数

要求：25.0 万 ≤ 单机拐点 × 16 × 0.65
得到：单机拐点 ≥ 24,038 QPS
```

折扣系数 0.65 扣除的是单机压测测不到的开销：内部 RPC 的序列化与网络（约 15%）、跨机广播分发（约 5%）、路由查表与重定向（约 5%）、尾延迟叠加导致的有效吞吐下降（约 10%）。

配置区假设的单机能力是 30,000 QPS，与通过线的比值是 **1.25x**，说明容量模型自洽且有余量。脚本对这个比值大于 1 有断言——如果假设值低于通过线，说明容量模型自相矛盾，要么加机器要么提高性能目标。

**这条通过线是全部压测工作的靶心**：单进程稳定跑到 24,038 QPS 且 P99 未爆炸，3000w DAU 的容量论证就闭环了。

### 4.2 三层压测

#### 第一层 · 单函数基准

```bash
go test -bench='BenchmarkAdvance|BenchmarkSettle|BenchmarkHazard|BenchmarkYield' \
        -benchmem ./internal/farm/
```

| 函数（实现名） | 目标 | 为什么 |
| --- | --- | --- |
| `Advance`（`BenchmarkAdvance`） | < 500 ns/op，**0 allocs/op** | 每个请求都调用，是全系统最热的函数 |
| `settleTo`（`BenchmarkSettle`） | 随 `Advance` 热路径，**0 allocs/op** | 健康度结算主体，被 `Advance` 调用 |
| `scanHazard`（`BenchmarkHazard`） | < 200 ns/op，0 allocs | 每次结算调用两次，含最多 10 次哈希 |
| `hazardHit`（`BenchmarkHazardHit`） | < 10 ns/op，0 allocs | xxhash64 单次的理论值约 5 ns |
| `computeFinalYield`（`BenchmarkYield`） | < 20 ns/op，0 allocs | 纯整数运算，不应有任何分配 |

纳秒阈值为人工读 benchmark 输出时的参考（机器相关）；仓库内可证伪验收只断言 **0 allocs/op**（见 `advance_alloc_test.go`）。

`0 allocs/op` 比纳秒数更重要。它是 3.6 节 GC 优化的前提条件，而且是一个二元的、不会因机器不同而漂移的判据。

#### 第二层 · 单进程容量

压测客户端与服务端必须分在不同机器，否则测的是压测客户端。

阶梯加压，每档稳定运行 3 分钟：`1k → 5k → 10k → 15k → 20k → 25k → 30k → 40k QPS`。

**找 P99 拐点**。延迟对吞吐的曲线在拐点前平缓、拐点后指数上升。拐点而不是「最大 QPS」才是容量数字——最大 QPS 那个点上系统已经在排队，延迟不可用。

#### 第三层 · 全链路

三个场景：

| 场景 | 配置 | 观察 |
| --- | --- | --- |
| 稳态 | 4,000 机器人持续 30 分钟 | 内存是否持续增长、合并率是否稳定、有无慢速泄漏 |
| 洪峰 | 5 分钟内从 0 涨到 4,000 | Actor 冷加载是否打穿存储（3.7 节） |
| 故障 | 稳态中途 kill 服务进程 | 恢复时间、数据丢失量 |

### 4.3 机器人行为模型

**机器人必须按行为链驱动，不能无脑打单接口。** 打单接口能压出很高的 QPS，但那个数字只反映最快的那个接口，与真实容量无关。

真实行为决定了四个下游压力量：读写比、房间订阅分布、write-behind 合并率、Actor 加载与淘汰率。其中「逛好友」的比例尤其关键——它决定了跨 Actor 操作的占比，而跨 Actor 是整个系统里唯一有分布式协调开销的路径。

马尔可夫链的状态与转移概率：

| 当前状态 | 转移到 | 概率 |
| --- | --- | ---: |
| 登录 | 看自己农场 | 1.00 |
| 看自己农场 | 收获 | 0.30 |
| | 照料（浇水 / 除草 / 除虫） | 0.25 |
| | 播种 | 0.15 |
| | 逛好友 | 0.15 |
| | 商店 | 0.08 |
| | 下线 | 0.07 |
| 收获 | 看自己农场 | 0.60 |
| | 出售 | 0.40 |
| 出售 / 商店 / 播种 / 照料 | 看自己农场 | 1.00 |
| 逛好友 | 进入好友农场 | 1.00 |
| 进入好友农场 | 偷菜 | 0.45 |
| | 互助 | 0.30 |
| | 下一个好友 | 0.20 |
| | 回自己农场 | 0.05 |
| 偷菜 | 下一个好友 | 0.60 |
| | 互助 | 0.40 |
| 互助 | 下一个好友 | 0.70 |
| | 回自己农场 | 0.30 |
| 下线 | 停留 30—300 秒后重新登录 | 1.00 |

**这些概率不是拍脑袋的。** 「进入好友农场后偷菜 0.45 显著高于互助 0.30」这一条，依据是策划 11.4 节的验算结论：「访问好友的主要动机是偷菜，不是互助。单次偷菜的期望价值是单次互助的 19 倍。」策划文档已经算出了玩家的最优策略，行为模型就应该向它对齐。

转移概率作为压测工具的可调参数，上线后用真实埋点数据校准。

### 4.4 bench 时间档：策划预留给压测的旋钮

策划 3.2 节定义了四个时间档，其中 `bench`（`TIME_SCALE = 1/3600`）明确标注用途为「压力测试」。这是策划层专门为压测预留的接口，压测方案要用足它。

```text
白萝卜一轮  = 10 缩放小时 = 10 真实秒
一个作物日  = 24 缩放小时 = 24 真实秒
一个逻辑日  = max(24 秒, 5 分钟) = 5 分钟（策划 3.4 的下限生效）

5 分钟压测 = 12.5 个作物日 + 恰好 1 个逻辑日边界
```

一轮 5 分钟的压测因此可以完整覆盖：十余次完整种植循环（锄地 → 播种 → 照料 → 成熟 → 收获 → 清理）、一次逻辑日重置（每日上限归零、日常任务重抽）、多轮偷菜窗口的开闭。

**没有这个旋钮，压出同样的行为覆盖需要真实运行 12 天。**

代价是 3.5 节警告过的：`bench` 档会让 write-behind 合并率严重虚高，该指标必须换档单独测量。

### 4.5 压测客户端规模

```text
单地块单轮操作数 = 锄地 1 + 播种 1 + 收获 1 + 清理 1
                 + 浇水 3 + 除草除虫期望 2.2 = 9.2 次
单机器人频率     = 9.2 × 6 块地 / 10 秒 × 1.3（社交操作） = 7.2 次/秒
打到通过线所需   = 24,038 / 7.2 = 3,350 个机器人
压测客户端机器   = 1 台（按单台 5 万连接计）
```

**一台压测机就够**。这个结论对 3 周周期很重要——它意味着压测不受硬件条件限制，可以随时跑。

### 4.6 判定标准

| 指标 | 通过线 |
| --- | --- |
| 稳定吞吐 | ≥ 24,038 QPS |
| P99 延迟 | < 50 ms（服务端内部，不含网络） |
| P999 延迟 | < 200 ms |
| 系统错误率 | < 0.01% |
| GC pause P99 | < 5 ms |
| mailbox 深度 P99 | ≤ 2 |
| write-behind 合并率 | ≥ 5:1（须在 `fast` 档单独测） |
| 内存稳定性 | 30 分钟稳态无持续增长 |

**「系统错误率」不包含业务失败。** 「水分已充足」「本轮已偷过」这类返回是玩法的正常组成部分（策划 8.4 明确要求把它们作为失败处理），压测中会大量出现，不应计入错误率。压测工具必须区分「协议层 / 系统层错误」与「业务层拒绝」，否则错误率指标会完全失真。

### 4.7 外推方法与它的三条局限

```text
集群吞吐估计 = 单机实测拐点 × 台数 × 0.65
```

压测报告里必须同时写明这三条局限，否则外推就是自欺：

1. **单机压测测不到分布式故障**：网络分区、跨机时钟偏差、Redis 主从切换、路由表分发延迟，这些在单机上一个都不会出现
2. **跨 Actor 操作的成本被低估**：单机压测中所有 Actor 在同一进程，跨 Actor 消息是本地 channel（纳秒级）；集群下约 15% 的跨 Actor 操作要走网络（毫秒级）。折扣系数试图补偿这一点，但它是估计不是测量
3. **线性外推假设无共享瓶颈，而这不成立**：MySQL 和 Redis 是全集群共享的。**逻辑层线性扩展不等于系统线性扩展。** 因此除了 FarmServer 的单机压测，必须单独压 MySQL 分片的写能力和 Redis 的读能力，用实测值替换 [capacity-model.py](capacity-model.py) 配置区 C 的假设并重跑

### 4.8 故障演练

| 演练 | 期望行为 |
| --- | --- |
| kill 一个 FarmServer 进程 | 客户端收到 `Kick` 并重连，30 秒内恢复；C 档数据丢失 ≤ 30 秒；A/B 档零丢失 |
| Redis 主库切换 | Actor 冷加载短暂失败并重试；已驻留 Actor 不受影响 |
| MySQL 注入慢查询 | write-behind 队列积压但不阻塞玩法路径；积压超阈值触发告警 |
| 注入 100 ms 网络延迟 | 跨 Actor 动作延迟上升但不触发 5 秒超时 |
| 单个农场 200 人同时偷菜 | mailbox 深度上升但不失控；40% 额度严格不被突破 |

最后一项同时是策划 13.4 节场景三的极限版本，兼作正确性验证。

## 5. 3 周内的实际执行计划

3 周做不完上述全部内容。取舍如下：

**必做**

- 第一层单函数基准（成本极低，`go test -bench` 而已，但产出的 `0 allocs/op` 结论很有分量）
- 第二层单进程容量，找到 P99 拐点，与 24,038 的通过线对照
- 简化版第三层：单机 + 3,350 机器人 + 稳态 30 分钟
- 故障演练的第一项（kill 进程）

**降级**

- MySQL 和 Redis 的独立压测降级为「用 `fast` 档跑一轮，实测合并率，回填脚本」
- 洪峰场景降级为「观察冷启动阶段的加载 QPS 曲线」，不做完整的雪崩演练

**不做**

- 真实多机集群压测（没有机器）
- 网络分区、主从切换演练

### 报告的核心是优化前后对比

压测报告里最有说服力的不是最终数字，而是**优化过程的对比表**。计划做四轮，每轮只改一件事：

| 版本 | 优化项 | QPS | P99 | 单机连接 | allocs/op |
| --- | --- | ---: | ---: | ---: | ---: |
| v0 | 基线（朴素实现） | 待测 | 待测 | 待测 | 待测 |
| v1 | 广播一次编码 + 按网关分组 | | | | |
| v2 | 去掉 per-connection goroutine | | | | |
| v3 | `advance()` 零分配 + `sync.Pool` | | | | |
| v4 | 写合并（2 ms 窗口） | | | | |

每轮只改一件事，是为了让每一行的收益可归因。一次改四项然后说「性能提升了 5 倍」，说服力远不如四行各自有明确归因的表格。

报告还应包含一份**未达成项清单**：哪些优化想做但没时间做、预期收益多少。承认边界比假装完备更可信。
