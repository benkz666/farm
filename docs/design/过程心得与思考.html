Internship Project Retrospective

从完成项目，
到理解工程决策

一次关于工作流、复杂度、AI 能力边界与架构演进的开发复盘。真正的成长，不只是把系统做出来，而是开始理解每一个选择背后的代价。

向下阅读
01

没有最好的工作流，只有最适合当下的工作流

我先后经历了“太灵活、太笨重、再回到轻量”的过程。最终发现，工作流不是教条，而是一种需要随任务特点和风险动态调整的控制工具。

探索期

grill-me

形式轻量、反馈快速，但流程也比较灵活。使用中我发现，前期讨论非常重要：如果目标、交付物和收敛条件没有约定清楚，AI 很容易沿着偏离预期的方向继续展开。

轻量，但依赖前期约定
框架期

Superpowers

先设计、再拆解、后实现和验证，适合搭建核心架构或进行大规模调整，过程更加稳健；但用于小改动时流程偏重，时间与 Token 成本也比较高。

稳健，但小改动偏重
迭代期

Cursor + Codex Plan

小步计划、局部修改和定向验证，更适合 Bug 修复与快速迭代优化；但工程规范、Review 强度和测试边界需要由自己定义并补齐。

快速，但规范需自行定义
MY TAKEAWAY 高风险或较大规模的变更，更适合在目标、边界和验收标准约定清楚后采用重流程；Bug 修复与局部迭代则适合快速、轻量的流程。流程可以灵活切换，但关键约束和验证证据不能省略。
02

没有银弹：复杂度不会消失，只会被重新分配

每一个设计都在解决旧问题，同时制造新的治理成本。工程选择的核心，不是消灭复杂度，而是决定让哪里承担复杂度。

Actor 串行决策多人并发写收敛为单一权威顺序
→
热点与排队同步 IO 会阻塞 mailbox，热点农场需要单独治理
跨农场分阶段事务把一次远程操作拆成预占、权威裁决与幂等结算
→
补偿与不确定状态必须处理超时、重复消息、结果未知和失败后的资源释放
Redis 异步落库请求快速确认，吸收瞬时流量并合并写入
→
积压与重放增加最终一致性、消费幂等、顺序和故障恢复问题
快照 + 增量同步正常链路只传 FarmDelta，降低全量状态传输成本
→
缺口检测与降级恢复需要维护 farm_seq、增量缓冲，并在历史淘汰后回退快照
误区“优化完成”不代表问题消失，往往只是问题换了一个位置。
判断标准把复杂度放到可观测、可验证、能够恢复和治理的位置。
03

AI 放大执行效率，但关键边界仍由人决策

AI 改变的首先是实现成本，而不是正确性的归属。它可以快速理解代码、扩展方案空间、实现修改并补充测试；但问题是否值得解决、哪些约束不可突破，以及什么证据足以支撑结论，仍然必须由人定义。

AI CAN EXECUTE

把意图转化为候选与证据

建立上下文阅读代码、文档与历史决策
扩展方案空间生成多个可比较的实现路径
执行与实验修改代码、复现 Bug、运行测试
形成可审查证据输出差异、指标、风险与结论
证据回传⇄约束下发
HUMAN MUST OWN

定义问题 · 进行取舍 · 验收结果

定义真正的问题选择目标，而不是追逐表面症状
声明系统不变量明确任何优化都不能破坏的底线
承担工程取舍在性能、成本、复杂度与风险间选择
验收最终结果用证据判断调整、迭代还是收敛
人先定义问题、边界和成功标准，AI 在边界内探索、实现并生成证据；人再依据结果决定继续调整、进入下一轮迭代，还是让方案收敛。
04

架构设计决定系统能走多远，边界越晚补成本越高

回看早期 Git，后期几次大改并不是在增加新业务和玩法，而是在偿还最初没有划清的协议、服务职责、写入路径与一致性边界。

血的代价

最初引入消息队列，是为了让访客农场发出请求后继续处理其他操作，不必同步等待主人农场。但一次互助或偷菜因此变成：访客预占并落库 → 消息队列转发 → 主人裁决并落库 → 消息队列返回结果 → 访客结算再落库。消费者还要等当前业务与持久化完成后才继续取下一条消息，可靠性有了，热路径却被拉长并逐步串行化。

架构问题很少在功能联调时立即报错，它更常在扩容、压测和故障恢复时集中收取利息。
Git 回溯：一次重构触及 159 个文件
01统一 Protobuf 协议原问题：HTTP 每次调用都携带请求头和鉴权信息，JSON 还会重复传输字段名、把数字编码成文本；大量高频小消息中，固定报文和多次解析的开销很明显。
重构收益：Protobuf 使用紧凑的二进制字段编号，配合长连接与批量消息，减少传输字节、连接开销和重复编解码。
02五个服务收敛为三个原问题：服务按技术功能拆得过细，一次农场操作还要调用任务服务推进进度、调用社交服务判断好友，链路跳数和故障点不断增加。
重构收益：登录鉴权并入接入服务，任务、邮件等并入农场服务；关联业务在同一领域内完成，减少跨服务调用，并明确数据由谁负责。
03重构农场写入路径原问题：每次操作都在农场串行队列中同步等待落库；跨农场还要经历预占、主人裁决、访客结算三次保存，并发访客只能排队。
重构收益：串行区只完成内存决策，持久化交给可靠异步链路与批量提交，避免数据库延迟阻塞整个农场。
04缩短跨农场链路原问题：访客请求与主人裁决结果都要各绕行一次消息队列，消费者等待业务落库后才继续取消息；基线中 1 人约 2.1s，5 人已大量 5s 超时。
重构收益：农场服务之间通过长连接直接传递请求与结果；幂等票据和可靠重投单独负责故障恢复，既缩短链路又保留可靠性。
THE REAL GROWTH

从“让系统跑起来”，到理解它为什么能够正确、稳定地演进。

这次项目真正的收获，不只是完成了一套系统，而是开始形成自己的工程判断：在不确定中识别真正的问题，在约束中权衡代价，并用可验证的结果持续修正、迭代和收敛每一次选择。
