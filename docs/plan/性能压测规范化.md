# 农场项目性能压测规范化方案

## 一句话思路

后端代码不动。已经埋好的指标现在没人收集，所以先补一套 Prometheus + Grafana 把它们显示出来；再用三种业界通用工具分别从「登录」「实时连接」「服务间调用」三个入口施压，加上项目里已有的两个自研压测器负责跨农场同步；最后在 kind 集群上把 Pod 资源写死，测出单副本能扛多少、加一个副本能涨多少，把这两个数字回填进已有的容量估算脚本，得出 3000w DAU 需要多少台机器。

## 现在有什么、缺什么

已经有的，直接用，不重做：

- 后端三个服务都已经在一个独立的运维端口上暴露了 Prometheus 指标和 Go 性能分析入口（gateway 是 9302、社交服务 9304、农场服务 9310，路径分别是 `/metrics` 和 `/debug/pprof/`）。指标覆盖了 WebSocket 连接数、每个命令的耗时分位、农场逻辑的排队深度、组提交的批次数等 19 项。
- `farmctl bench` 是项目自带的跨农场压测器，能让 N 个访客同时给同一个农场浇水并统计端到端延迟，里面已经处理了真并发发射、预热轮、分位数统计、失败码分类、失败率过高自动标注数据不可信这些细节。
- `farmctl hotspot` 能绕开 200 好友上限，用最多一万个虚拟访客直接冲击单个农场。
- `docs/design/capacity-and-benchmark.md` 和 `capacity-model.py` 已经有完整的 3000w DAU 容量推导（峰值在线 166.7 万、16 个 MySQL 主分片、压测通过线 ≥24038 QPS），但里面所有实测栏位都还是「待测」。

缺的，就是这次要补的：

- 指标没人采集，仓库里没有任何 Prometheus 或 Grafana 配置，看不到任何曲线。
- 没有任何业界通用工具的痕迹。看不到 k6、ghz 这类一眼能认出的东西。
- 资源没固定，所以「单机能扛多少」这个数字没有意义，也没有水平扩展的数据。
- 没有任何实测报告文件。

## 一个重要约束：压测要遵守限流，而不是绕开它

Gateway 对每条 WebSocket 连接有令牌桶限流：桶容量 20、每秒补充 10 个，连续被拒 5 次就断开连接。这些值写死在代码里。

**不改它。** 压测遵守这个规则，靠增加连接数而不是提高单连接速率来放大总吞吐。理由有两条：

- 真实玩家不可能每秒点 10 次以上，遵守限流才是模拟真实负载。
- 不改代码就少一个"压测环境和生产环境不一致"的质疑点。

具体做法是每个虚拟用户独占一条连接、每秒最多发 8 条命令（留 20% 余量避免踩线）。1000 条连接就是 8000 QPS，1 万条连接就是 8 万 QPS，完全够用。报告里要写明这一点：**测的是「N 条连接 × 每条 8 QPS」，这正是真实玩家的行为模型**。

顺带说明另外几个写死的上限，压测时要知道它们存在：单条消息最大 64 KB、读超时 90 秒、心跳间隔 30 秒、每条连接的推送队列深度 64（满了就主动关掉这条慢连接）。最后这一条在「慢客户端」场景里是被测对象，不是意外故障。

## 二、每个工具测什么业务

这是整个方案最需要向评委讲清楚的部分。分工的原则是：**游戏状态机相关的路径用项目自带工具，通用链路用业界工具**。

因为浇水有水分窗口、作物会成熟枯萎、种地要花种子钱，k6 这类通用工具很难长时间维持一个可持续的写循环；而项目自带的 `farmctl bench` 已经把补种、收获、卖果实、推进时钟这套编排全做好了。这个分工本身就是一个专业的技术判断。

### k6 场景一：注册与登录（`auth_load.js`）

- **对应基础要求**：账号与登录。
- **打的接口**：`POST /api/register` 和 `POST /api/login`。
- **服务端实际走的路**：Gateway 收请求 → 校验用户名密码 → 写 MySQL 的账号表 → 在 Redis 里签发会话。
- **为什么值得单独测**：密码哈希是纯 CPU 密集操作，登录洪峰的资源曲线和游戏内操作完全不同。容量文档里假设「人均每天登录 4 次」，登录服务的峰值和游戏峰值不在同一时刻，这是需要单独定容量的。
- **SLO 阈值**：95% 请求 200 毫秒内完成，失败率低于 0.1%。

### k6 场景二：实时连接承载（`ws_capacity.js`）

- **对应基础要求**：多人实时同步的连接基础。
- **做的事**：每个虚拟用户建一条 WebSocket 连接 → 握手（带登录拿到的 token）→ 进入自己的农场 → 之后每 30 秒发一次心跳，长期保持在线。
- **服务端实际走的路**：Gateway 升级连接、校验会话、把「这个玩家在哪条连接上、订阅了哪个农场」登记进连接注册表（Redis）。
- **测出来的关键数字**：单个 Gateway 副本最多能挂多少条连接、每条连接占多少内存。容量文档里假设是「单网关 25 万连接、每条连接 4608 字节」，这个场景就是去验证这两个假设数。
- **怎么加压**：阶梯式增加连接数直到内存或连接数触顶，观察拐点。
- **SLO 阈值**：握手 95% 在 500 毫秒内完成，连接掉线率为 0。

### k6 场景三：农场快照读路径（`ws_read_throughput.js`）

- **对应基础要求**：种植循环与地块状态展示。
- **做的事**：已连接的玩家反复拉取自己农场的完整快照（进入农场、同步农场两个命令）。
- **服务端实际走的路**：农场服务的房间逻辑从内存里读当前状态，顺便做一次「惰性推进」计算（根据经过的时间推算作物长到哪一步、水分掉了多少），然后编码成 JSON 返回。**全程不碰数据库**。
- **为什么值得单独测**：这条路是纯内存加纯 CPU，它测出来的就是房间串行处理的 CPU 吞吐上限。容量文档里最关键的假设「单个农场服务 3 万 QPS」主要就靠这个场景来验证。
- **SLO 阈值**：95% 在 100 毫秒内，99% 在 200 毫秒内。

### ghz 场景：好友判定（服务间 gRPC）

- **对应基础要求**：好友玩法，以及跨农场操作的权限前置校验。
- **打的接口**：社交服务的「两人是否为好友」这个一元 gRPC 调用。它是纯读、幂等的，可以无限次重复而不产生任何副作用，非常适合做纯吞吐压测。
- **服务端实际走的路**：先查农场服务的进程内缓存，没命中查 Redis 的好友列表缓存，还没命中才落 MySQL 的好友表。
- **为什么值得单独测**：每一次帮好友浇水或者偷菜，都要先判一次好友关系。架构设计里专门做了三层缓存把这个判定挡在数据库之外，这个场景就是去量化三层缓存的效果——分别在「缓存全热」和「冷启动」两种状态下压，对比 QPS 与延迟差距。
- **顺带验证**：内部服务间 gRPC 的裸吞吐上限，以及 protobuf 相比原来 HTTP + JSON 的收益。

### farmctl bench 场景：跨农场实时同步（核心）

- **对应基础要求**：「多人在同一农场中操作时，需实时同步地块状态」——这是整个项目最核心的一条要求。
- **做的事**：让 1、5、10、20、50 个访客在同一时刻给同一个主人的农场浇水，测每个请求从发出到收到应答的端到端延迟。
- **服务端实际走的路**：访客的命令进 Gateway → 转给访客所在的农场服务 → 跨进程转给主人所在的农场服务做裁决 → 裁决结果进组提交批次写库 → 同时把地块变化广播给房间里所有在线访客。这是全项目最长、最复杂的一条链路。
- **测出来的关键结论**：延迟是否随访客数线性增长。架构重构文档里最主要的收益论断就是「重构后延迟几乎不随访客数增长」（重构前 10 个访客队尾要 50-150 毫秒，重构后应该稳定在 6-7 毫秒）。这条曲线是整份报告里最有说服力的一张图。
- **执行方式**：不改代码，用 `-visitors` 参数跑五档，输出重定向到文件，由 `run-suite.sh` 整理成 CSV 再画图。

### farmctl hotspot 场景：热点农场极限

- **对应场景**：大 V 玩家的农场，两百个好友同时来访。
- **做的事**：用最多一万个虚拟访客同时冲击单个农场。
- **测出来的关键结论**：单个农场的串行处理区在极端热点下的吞吐上限和退化曲线，以及组提交在高并发下能把多少个玩家的写合并进一个数据库事务。
- **注意边界**：虚拟访客没有真实账号和 WebSocket 连接，所以这个场景只测主人侧的裁决、好友鉴权、组提交和结算票据，**不代表万人广播能力**。报告里必须说明这个边界，不能夸大。

### pprof 与 Grafana：找瓶颈在哪个函数

- 压测到峰值时，抓一次 30 秒的 CPU 采样和一次堆内存快照，生成火焰图，直接定位到最耗 CPU 的具体函数。
- Grafana 看板同时显示压力、延迟、排队深度和资源占用四行，让「QPS 上去了但延迟没涨」和「延迟涨了是因为排队」这两种情况一眼可分。

## 三、监控栈（第一步，改动最小）

在 `deploy/compose.yml` 里新增一个 `obs` profile，不影响现有的启动方式：

- **Prometheus**：抓三个服务的运维端口，同时开启接收远程写入，这样 k6 的压测端指标也能写进同一个 Prometheus。
- **Grafana**：用自动挂载配置把数据源和看板都预置好，启动即可用，不需要手工点击配置。
- **MySQL、Redis、容器三个 exporter**：补上存储层和容器资源层的指标。

新增文件放在 `deploy/observability/`，`Makefile` 加 `obs-up` / `obs-down` 两个目标。

看板 `farm-overview.json` 分四行，顺序刻意和报告章节一致：

- 第一行「压力」：WebSocket 在线连接数、各命令的 QPS、注册登录 QPS。
- 第二行「延迟」：各命令的 p50/p95/p99、错误码分布。
- 第三行「瓶颈」：农场逻辑的排队深度、组提交的合并率、广播的目标人数分布、数据库落盘耗时。
- 第四行「资源」：CPU、内存、GC、容器 CPU 限流时长、MySQL 与 Redis 状态。

**组提交合并率不需要改后端代码就能算出来**：现有的三个计数器（批次数、批内农场数、合并前的逻辑请求数）在 Grafana 里用一个除法表达式就能得到平均批大小与合并率：

```promql
rate(farm_committer_requests_total[1m]) / rate(farm_committer_batches_total[1m])
```

这正好对应架构文档里那句「合并率才是核心监控指标」。

## 四、固定 Pod 资源

所有服务的 `requests` 和 `limits` 设成**完全相同的值**。这样 Kubernetes 会把 Pod 归到**保障型服务质量等级**，不会被驱逐、不会和别的 Pod 抢资源，每次测量结果才可复现。这是压测环境的标准做法，也是报告里必须写明的一条。

固定档位如下：

- **gateway**：CPU 2 核、内存 2Gi。它主要吃网络和连接内存，不做重计算。
- **farmsvr**（农场服务）：CPU 2 核、内存 4Gi。内存给得多是因为它要常驻活跃玩家的农场状态（容量模型里每个活跃玩家约 9.6 KB）。
- **socialsvr**（社交服务）：CPU 1 核、内存 1Gi。好友操作是极低频写、高频读，缓存挡住后压力很小。
- **MySQL**：CPU 2 核、内存 4Gi。
- **Redis**：CPU 1 核、内存 2Gi。
- **Prometheus**：CPU 1 核、内存 2Gi。
- **Grafana**：CPU 0.5 核、内存 512Mi。

两点必须注意：

- **k6 压测器跑在 kind 集群之外的宿主机上**，不占集群资源。压测机自身 CPU 使用率要保持在 70% 以下，否则测的是压测机的瓶颈。这一点在报告里要给出压测机的 CPU 数据作为证据。
- **CPU 上限会触发 CFS 限流**。设了 CPU limit 之后，容器用满配额就会被内核强制暂停，表现出来是延迟突刺，很容易被误判成程序有问题。所以看板第四行必须放容器 CPU 限流时长这个指标，压测时同步观察。这个细节是区分「做过真压测」和「跑了个脚本」的分水岭。

单副本全跑起来大约需要 9.5 核、15.5Gi。**双副本水平扩展测试时** gateway 和 farmsvr 各加一个副本，需要再多 4 核、6Gi，所以 Docker Desktop 至少要分配 14 核、24Gi 内存。如果本机资源不够，把上面每个档位等比减半（gateway 1C/1Gi、farmsvr 1C/2Gi 等），结论仍然成立，只是绝对数字变小——**报告里只要写清楚档位，外推时按比例换算即可**。

## 五、kind 集群与三轮测试

新增 `deploy/k8s/` 目录：

- `kind-cluster.yaml`：一个控制节点加两个工作节点。
- gateway 用普通 Deployment，可以多副本，也可以挂 HPA 自动扩缩容。
- **farmsvr 必须用 StatefulSet，不能用普通 Deployment 多副本**。原因是农场服务按 UID 分片，每个实例只认领属于自己的那一半玩家，实例身份必须稳定。StatefulSet 给的 Pod 名字是 `farmsvr-0`、`farmsvr-1`，正好对应路由表里的 `farm-0`、`farm-1`。
- 路由表用 ConfigMap 挂进去。项目里已经有现成的两分片示例（前 512 个逻辑分片给 `farm-0`、后 512 个给 `farm-1`），直接用。
- 监控用 Helm 装 `kube-prometheus-stack`，一条命令带齐节点指标、Kubernetes 对象指标和 Grafana，然后导入第一步做好的同一份看板。

**一个值得写进报告的架构结论**：HPA 只能加在 gateway 上。农场服务因为分片路由和单写者模型，副本数变化必须改路由表并迁移房间，无法自动扩缩容。主动指出这个限制、并说明它是分片架构的必然代价，比假装什么都能自动扩容更有说服力。

三轮测试按顺序做：

- **第一轮，单副本容量基线**。农场服务 1 副本、HPA 关闭、资源按上面档位固定。测出四个数字：最大连接数、读路径 QPS 上限、跨农场写路径的 p95/p99、以及首个瓶颈出现在哪里（CPU 打满、数据库落盘变慢、还是排队变长）。同时必须确认容器没有被 CPU 限流。
- **第二轮，水平扩展效率**。农场服务从 1 副本加到 2 副本、分片各承担一半，重复同样的压测。算扩展效率等于吞吐增长倍数除以副本增长倍数。如果明显低于线性，说明瓶颈已经转移到 MySQL、Redis 或路由层，这个发现本身就是有价值的瓶颈分析结论。这一轮要确认压测流量真的落到了两个实例上（看两个 Pod 的指标是否都有负载），否则等于没测跨实例。
- **第三轮，故障恢复**。压测进行中直接删掉一个农场服务 Pod 和一个 gateway Pod，测重连耗时、有没有丢消息、状态多久收敛一致。用 `kubectl delete pod` 就够，不引入 Chaos Mesh 增加复杂度。

## 六、执行规范与最终报告

新增 `bench/run-suite.sh`，把压测规范写进脚本而不是靠自觉执行：

- 每次运行先记录环境指纹：git 提交号、镜像版本、CPU 型号、内核版本、Go 版本、Pod 资源档位，全部写进结果文件。没有环境指纹的压测数据是不可复现的。
- 每个档位先预热，然后跑三次取中位数，避免单次抖动被当成结论。
- 按目标负载的 1%、10%、30%、60%、100%、120% 阶梯升压，找拐点，而不是一上来就打满。最后在 100% 负载下做一次一到两小时的稳定性测试，看有没有内存泄漏或性能衰减。
- 峰值时自动抓 CPU 采样和堆快照存盘。

最终产出 `docs/benchmark/report.md`，章节顺序和看板分行一致：

- 测试环境与方法：环境指纹、Pod 资源档位、SLO 定义、工具版本、压测机隔离证据。
- 单副本容量上限：四个关键数字。
- 瓶颈分析：Grafana 截图加火焰图，指出首个瓶颈的具体位置和函数。
- 水平扩展效率与 HPA 行为。
- 故障恢复与数据一致性。
- **回填容量模型**：把实测出来的「单农场服务 QPS」「单网关连接数」「组提交合并率」三个数字，替换掉 `capacity-model.py` 里原来靠假设填的 30000、250000、5:1，重跑脚本得出 3000w DAU 的真实机器清单，和原估算对比并解释偏差原因，最后说明保留了多少容量余量（目标是 30% 到 50%）。

最后这一步是整个方案的价值所在：它把「估算 → 压测 → 修正估算」闭成一个环，而不是只交一堆孤立的压测数字。架构重构文档里唯一还没完成的待办 P8 正是这件事。
