# API 文档与前端接口性能基准计划

## 一、目标

建立统一 API 文档入口，并让前端实际调用的每个接口都具备明确测试状态：

- HTTP 使用 OpenAPI 3.1 + Swagger UI。
- WebSocket 使用 AsyncAPI 3.0。
- 内部 gRPC 从 proto 自动生成文档。
- 每个前端接口至少执行一次自动化基线测试。
- 高频、慢路径、数据库写、跨服务和热点接口进一步阶梯加压，得到最大稳定 QPS。
- 单接口结果产出 CPU、MySQL、Redis和分配内存/请求，作为后续3000万DAU容量模型的实测输入。
- 不把单接口基准描述成完整的3000万DAU全链路验证。

## 二、API 文档实现

### 文档入口

新增开发环境文档路由：

- `GET /docs/`：统一导航。
- `GET /docs/http/`：Swagger UI。
- `GET /docs/ws/`：AsyncAPI HTML。
- `GET /docs/grpc/`：gRPC HTML。
- `GET /docs/openapi.yaml`：OpenAPI源文件。
- `GET /docs/asyncapi.yaml`：AsyncAPI源文件。

启用条件：

```text
FARM_ENV=dev
FARM_ENABLE_API_DOCS=1
```

其他环境不注册这些路由并返回404。Vite和Nginx代理 `/docs/` 到Gateway。

Swagger UI使用本地 `swagger-ui-dist` 静态资源；AsyncAPI使用固定版本CLI和HTML模板生成单页；gRPC使用 `protoc-gen-doc`，运行时不依赖CDN。[Swagger UI官方安装方式](https://swagger.io/docs/open-source-tools/swagger-ui/usage/installation/)、[AsyncAPI HTML生成方式](https://www.asyncapi.com/docs/tools/generator/usage/)。

### 文档内容

OpenAPI覆盖：

- `POST /api/register`
- `POST /api/login`
- `GET /i/{token}`
- `POST /api/debug/advance`，标注为仅开发环境

AsyncAPI覆盖前端实际使用的38个请求命令：

- 会话：100、102、200、202、204
- 地块：206、208、210、212、214、216、218、220、222
- 经济：302、304
- 社交：400、402、404、406、408、410、412、414、416、418
- 宠物：500、502、504
- 任务/邮件/图鉴：600、602、604、606、608、610、612、614、616

同时覆盖6个前端接收的推送：

- 9000 FarmDelta
- 9002 PlayerDelta
- 9004 MailNotify
- 9006 SessionKick
- 9008 TaskNotify
- 9010 PushBatch

gRPC文档覆盖现有全部proto服务，但只有核心跨服务调用进入直接性能测试，其余通过前端链路间接覆盖。

所有UID、farm_seq、mail_id等64位JSON标识定义为十进制字符串，不允许标注为JavaScript number。

### 文档与测试关联

每个OpenAPI/AsyncAPI操作增加：

```yaml
x-performance-tier: ladder | baseline | delivery | functional-only
x-performance-scenario: 对应脚本场景名
x-performance-reason: 高频/慢路径/写库/跨服务/热点/低频
```

建立接口目录，记录：

- 前端方法名；
- HTTP路径或WS命令号；
- operationId；
- 请求和响应结构；
- 数据前置条件；
- 是否可重复；
- 测试等级；
- 自动化场景；
- 当前测试结果。

新增：

- `make api-docs`：校验并生成文档。
- `make api-docs-check`：重新生成并检查漂移。
- 契约测试确保前端命令常量、服务端命令和AsyncAPI三者一致。

### C级：推送和异常链路

推送不使用“请求QPS”，改为验证发送吞吐、送达率和延迟：

| 推送 | 触发方式 | 指标 |
|---|---|---|
| FarmDelta 9000 | 地块状态变化 | 生成到客户端接收延迟、送达率 |
| PlayerDelta 9002 | 金币/背包变化 | 送达率、顺序 |
| MailNotify 9004 | 生成测试邮件 | 送达率 |
| SessionKick 9006 | 同账号第二次登录 | 踢下线延迟 |
| TaskNotify 9008 | 推进任务 | 送达率 |
| PushBatch 9010 | 多条推送合并 | 解包正确性、批量吞吐 |

另外覆盖：

- 未认证请求；
- 非法字段和未知字段；
- 业务错误码；
- 限流；
- 请求超时；
- WebSocket断线重连；
- client_seq响应匹配；
- 64位ID精度；
- 重复领取和重复提交。

## 四、自动化测试框架

### 测试目录和数据

建立统一场景目录和测试目录：

- HTTP、WebSocket使用k6。
- gRPC AreFriends使用ghz。
- 跨农场和热点场景复用farmctl。
- 测试账号、好友对、农场状态、邮件、任务和资产在压测前生成到 `.run/bench-data/`。
- 登录与WebSocket测试使用预置账号池；测量窗口内不得注册账号。
- 所有测试结果写入 `.run/bench-results/<run-id>/`。

通用WebSocket测试驱动支持：

```text
SCENARIO=<operationId>
TARGET_QPS=<目标>
DURATION=<时长>
DATA_FILE=<夹具>
```

每个场景包含：

- setup：选择合法夹具；
- execute：只发送目标接口；
- verify：校验响应和状态；
- cleanup/reset：在测量窗口外恢复数据；
- expected_errors：区分业务拒绝和系统错误。

### 阶梯规则

A级接口：

1. Auth从10 req/s开始，其余接口从100 req/s开始。
2. 每档翻倍，最多8档。
3. 每档预热1分钟、稳定3分钟。
4. 首次失败后补测最后通过档和失败档的中点。
5. 边界档重复3次，取中位数。
6. 单连接最多8命令/秒，提高QPS必须增加连接数。

稳定档必须满足：

- 实际QPS达到目标的95%以上；
- 系统错误率低于0.1%；
- 无非预期掉线；
- Login：P95<500ms、P99<1000ms；
- 读接口：P95<100ms、P99<250ms；
- 本地写：P95<150ms、P99<300ms；
- 跨服务：P95<250ms、P99<500ms；
- CPU不持续超过80%；
- 内存和后台队列不持续增长。

B级接口：

- 10 VU、持续1分钟；
- 只要求功能成功、延迟可记录、资源无异常；
- 一次性操作通过夹具池完成，不为追求QPS反复请求非法状态。

## 五、服务需求采集

补充Go process/runtime Prometheus collector，结合现有MySQL和Redis exporter。每个隔离接口先采集60秒空闲基线，再计算：

```text
CPU ms/请求
= (CPU秒增量 - 空闲CPU速率×测试时长) × 1000 / 成功请求数

分配B/请求
= (TotalAlloc增量 - 空闲分配速率×测试时长) / 成功请求数

MySQL操作/请求
= (MySQL查询增量 - 空闲查询速率×测试时长) / 成功请求数

Redis操作/请求
= (Redis命令增量 - 空闲命令速率×测试时长) / 成功请求数
```

跨服务接口分别记录Gateway、Farm和Social的CPU/请求，并计算总CPU需求。

边界档自动保存：

- k6或ghz原始JSON；
- Prometheus起止快照；
- CPU profile；
- heap profile；
- Grafana时间范围；
- 环境指纹和git提交号。

## 六、验收与报告

文档验收：

- `/docs/`可以离线打开三个文档页面。
- 所有前端实际调用接口均有契约。
- 所有前端请求接口均绑定一个自动化测试场景。
- 所有推送均有触发和送达测试。
- 文档与前后端命令常量不存在漂移。
- 非开发环境不暴露文档。

性能报告固定输出：

| operationId | 协议 | 等级 | 平均 | P95 | P99 | 错误率 | CPU ms/请求 | MySQL/请求 | Redis/请求 | 分配B/请求 | 最大稳定QPS | 瓶颈 |
|---|---|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|---|

报告结论分为：

1. 前端接口覆盖率；
2. 各接口服务需求；
3. A级接口最大稳定QPS；
4. 慢接口和首个资源瓶颈；
5. 推送可靠性；
6. 未达到SLO的接口；
7. 可输入3000万DAU排队模型的实测参数。

## 假设

- “覆盖全”指前端实际调用的HTTP、WebSocket请求和推送全部有文档及自动化测试，不代表每个接口都进行不合理的极限压测。
- 内部gRPC全部生成文档，AreFriends直接压测，其他gRPC通过对应前端链路间接覆盖。
- 本计划只形成单接口性能基线，不直接宣称完成3000万DAU全链路验证。
- 现有未提交的bench、监控和部署改动均保留并增量修改。
