# 第二层：业务链路性能测试计划

## 总体思路

第二层不追求覆盖所有 API，而是覆盖“用户真正连续完成的业务”。一周内完成 7 条核心链路，每条先独立验证，再按比例组成混合负载。

统一流程：

```text
预置账号和业务状态
→ 登录
→ WebSocket 建连与握手
→ 执行业务链路
→ 校验响应、推送和最终状态
→ 正常退出或断线重连
```

注册账号、创建好友、推进作物时间等准备动作放在计时区间外；业务拒绝与系统错误分开统计。

## 必测业务链路

| 编号 | 业务链路 | 计时范围 | 重点验证 |
|---|---|---|---|
| L1 | 用户启动 | `Login → WS握手 → EnterFarm → TaskList → MailList` | 登录叠加建连、Redis 会话、Actor 冷加载、MySQL 连接池 |
| L2 | 本农场种植循环 | `Buy → Till → Plant → Water → Harvest → Sell → SyncFarm` | 读写混合、连续状态修改、经济数据一致性、落库队列 |
| L3 | 多人实时同步 | `A/B进入A农场 → A操作 → B收到FarmDelta → B执行SyncFarm → LeaveFarm` | 广播延迟、消息顺序、增量同步、离开后停止房间推送 |
| L4 | 好友建立与访问 | `SearchUser/GenShareLink → Request/Accept → FriendList → EnterFarm(friend)` | Social、Redis 好友缓存、数据库写后读、关系状态一致 |
| L5 | 跨农场互动 | `B进入A农场 → Water或Steal → A/B收到响应和推送 → A SyncFarm` | 最长跨服务链路、好友鉴权、热点 Actor、跨农场状态收敛 |
| L6 | 任务与邮件奖励 | `玩法操作 → TaskNotify → TaskList → TaskClaim → MailNotify → MailList → MailClaim` | 异步通知、任务进度、奖励入账、重复领取幂等性 |
| L7 | 重连与状态清理 | `断开连接 → 重新建连/握手 → SyncFarm → 校验状态 → 再退出` | 旧连接释放、Redis presence 清理、断线期间增量补齐、无重复推送 |

低频的宠物切换、喂养、图鉴查询、邮件删除不单独做性能链路；它们保留功能冒烟即可。偷菜在 L5 中占较小比例，并额外用现有热点工具验证并发正确性。

## 负载设计与验收

### 独立链路

每条链路依次执行：

```text
10 VU 校准 3 分钟
→ 50 VU 5 分钟
→ 100 VU 5 分钟
→ 200 VU 5 分钟
```

L3、L5 增加同一农场热点档位：

```text
1主人 + 1、10、50名访客
```

每个 VU 独占一条 WebSocket，单连接业务命令不超过 8 次/秒；作物、任务、邮件和好友状态提前准备，不在计时期间调用全局调时接口。

### 混合负载

混合测试比例固定为：

| 链路 | 占比 |
|---|---:|
| L1 用户启动 | 5% |
| L2 本农场循环 | 40% |
| L3 实时同步 | 20% |
| L4 好友建立与访问 | 5% |
| L5 跨农场互动 | 15% |
| L6 任务与邮件 | 10% |
| L7 重连恢复 | 5% |

执行阶梯：

```text
100 → 300 → 600 → 1000 VU
```

每档预热 1 分钟、稳态 10 分钟；最后在最大通过档位的 60% 负载下运行 30 分钟稳定性测试。第二层用于验证业务组合和资源竞争，不把 1000 VU 等同于 3000 万 DAU；全量规模由第一层测得的单副本容量外推。

### 通过标准

- 普通业务步骤：P95 `<150ms`、P99 `<300ms`。
- 好友及跨农场步骤：P95 `<250ms`、P99 `<500ms`。
- L1 完整启动链路：P95 `<1.5s`。
- L7 重连并恢复状态：P95 `<2s`。
- 系统错误率 `<0.1%`，业务拒绝单独统计。
- FarmDelta、TaskNotify、MailNotify 丢失或乱序导致的状态错误为 `0`。
- 重复领取、重复结算、金币或仓库不一致为 `0`。
- LeaveFarm 后不得再收到新房间 Delta。
- 测试结束后 WebSocket 连接数回到基线；异常断线残留 presence 最迟在当前 2 分钟租约窗口后清除。
- CPU、内存、数据库连接池、Actor mailbox、Redis 延迟和后台落库队列不得持续恶化。

## 测试脚本与数据准备

- 新增一个业务链路 k6 脚本，按 `chain` 和 `step` 标签记录端到端及分步骤耗时；扩展现有协议封装以支持通用 WS 命令，不修改生产 API。
- 增加独立数据准备脚本，生成确定性用户名，提前建立账号、好友对、可操作地块、已完成任务和带附件邮件；正式测试只复用这些数据。
- k6 负责 L1、L2、L4、L6、L7 和混合负载；现有 `farmctl room/help/steal/bench/hotspot` 负责 L3、L5 的一致性与热点并发复核。
- 每个链路记录 `chain_latency`、`step_latency`、系统错误、业务拒绝、推送延迟、状态校验失败；Prometheus 同步记录连接数、连接池等待、Redis、MySQL、Actor mailbox、CPU、内存和 GC。

## 一周安排与交付物

1. 第一天：准备账号、好友、地块、任务和邮件数据，完成 L1/L2。
2. 第二天：完成 L3/L4，验证推送和好友状态。
3. 第三天：完成 L5/L6，接入跨农场、任务和邮件校验。
4. 第四天：完成 L7 和全部链路小流量校准。
5. 第五天：运行各链路 50/100/200 VU 独立测试。
6. 第六天：运行混合阶梯与 30 分钟稳定性测试，抓取峰值 pprof。
7. 第七天：整理报告和答辩图表。

最终报告只保留四类结果：

- 每条链路的 P95/P99、吞吐和错误率表；
- 混合负载下 QPS—P99—CPU 曲线；
- L3/L5 推送延迟与热点农场退化曲线；
- 发现的问题及证据，例如连接池等待、Redis 热点、多服务延迟叠加、读写互相影响和连接状态残留。

假设：沿用此前的一周工期；第二层侧重业务组合正确性与性能，不承担真实 3000 万在线连接的全量实压。
